# X66 — JSON-ESCAPE-FOLD: exact JSON escape-surface folding (negative full-frontier result)

Date: 2026-10-31. This report records the implementation, contract, red-team results, two complete fixture-specific frontier comparisons, the exact X61 repeat, live prior-art searches, and a bounded audit of current AI-mathematics claims. Receipts are in `bench/x66/receipts/`.

## Outcome at a glance

A new registered codec and tests were implemented. It folds only five lowercase JSON Unicode escape spellings (`\u003c`, `\u003e`, `\u003d`, `\u0026`, `\u0027`) to their literal ASCII characters inside valid JSON strings. A collision-free private-use marker before each replacement makes exact original spelling recoverable from the same message. The header also contains the full transform rule; the child is a complete TAGSTACK/SIBLING-TEMPLATE message.

**Exactness is achievable; a measured Pareto gain is not established.** The one-message envelope inverse passes its red-team checks. On both complete real SPDX-JSON fixture gates, the exact candidate is larger than the exact same-source TAGSTACK runtime-parent frontier plus SIBLING-TEMPLATE and is rejected. No strict win, fixture-leader change, or Pareto claim is made.

## Contract, domain, and formal boundary

For a nonempty, valid JSON string `s` of at most 80,000 UTF-16 code units that contains at least one supported lowercase escape, the planner:

1. validates JSON with `JSON.parse` without reserializing it;
2. scans JSON strings and replaces only the five exact lowercase escape spellings above with `M + c`, where `M` is a private-use Unicode scalar absent from `s` and `c` is its literal ASCII character;
3. emits a header naming both the marker code point and its literal character, followed by a complete measured parent message;
4. supplies a stateless inverse that reads the marker from the serialized header and reconstructs the precise lowercase six-character escape spelling.

All other code units are copied unchanged. Uppercase hex, quote/backslash/control escapes, and Unicode escapes outside the five-item subset are not rewritten. The encoder refuses invalid JSON, empty/over-cap input, and inputs with no supported escape. The private-use marker pool contains 137,468 scalars; because the source is bounded to 80,000 UTF-16 code units, at least one pool scalar is absent. Selection is deterministic: first absent scalar in BMP PUA, then supplementary PUA.

**Achievable:** on the stated UTF-8 fixture files, exact text restoration implies identical UTF-8 bytes; the serialized transform header plus restored child text is sufficient for the transform inverse, without encoder-side plan metadata. Red-team tests also cover supplementary-marker selection after deliberately placing every BMP PUA scalar in the JSON source.

**Boundary:** the code operates on valid JSON strings decoded as JavaScript strings, not arbitrary byte streams or alternate invalid UTF-8. Its hard local cap is 80,000 UTF-16 code units. The measured parent decoder is declared in-band and the parent message is included verbatim, but we did not test a native LLM as decoder and did not independently reconstruct all TAGSTACK child-parent internals from serialized bytes in a second language. No native-LLM decoding claim is made.

**Why the marker is necessary:** after JSON parsing, literal `<` and source spelling `\u003c` have the same JSON string value. A transform that drops this provenance without carrying a distinguishing symbol or equivalent side information cannot be byte-exact on both inputs. This codec explicitly carries that distinction in-band; it does not pretend the information is derivable.

## Implementation and search status

- Files: `src/lib/omega/json-escape-fold.ts`; registry key `json-escape-fold`; red-team runner `bench/x66/json-escape-fold-redteam.ts`; full gate `bench/x66/json-escape-fold-fullgate.ts`.
- Search: deterministic, non-greedy single pass; all supported occurrences are folded or none are. No subset search, candidate ranking, token-proxy threshold, or backtracking. Marker selection is deterministic, O(n + P) with `P = 137,468` bounded marker candidates, using a set of source scalars. JSON validation and transform are O(n). No wrapper-wide CPU/time budget is imposed; the module refuses sources over 80,000 UTF-16 code units. The full TAGSTACK parent measurements dominate runtime and are not given a new budget by this wrapper.
- Emission condition: source frontier and transformed frontier must both be exact and complete; the serialized transform envelope must parse; the transform inverse must exactly reproduce the source; direct `o200k_base` count of the *entire* transform contract plus complete child message must be strictly less than the same-source source frontier. Every refusal returns the source frontier message.
- Near-miss/failure classes are explicit: invalid JSON / over-cap / no supported escapes → identity plan refused; incomplete source frontier → fail closed; incomplete transformed frontier → fail closed; invalid marker target/header or inverse mismatch → fail closed; exact candidate with `M_candidate >= M_frontier` → exact fallback. Both measured fixtures reached the last class. Only a strict exact complete-message win can set `applied=true`.

## Prior art and novelty boundary

The code is **new as a repository implementation**, but the underlying operation is a narrow syntax-level escape fold with a literal provenance marker, not a new compression-theory primitive. It is adjacent to ordinary JSON escaping/unescaping and format-aware preprocessing. The stack audit found no exact same registered transform, but also found broad JSON, Unicode, dictionary, and markup coverage. No global novelty or Pareto-superiority claim is made. Relevant comparisons:

- Cheng, Lin & Sun, “SortComp (Sort-and-Compress),” DCC 2022, IEEE/SigPort: per-column sorting plus stored permutation tables for lossless matrices/tables: [IEEE](https://ieeexplore.ieee.org/document/9810714/), [SigPort](https://sigport.org/documents/sortcomp-sort-and-compress-towards-universal-lossless-compression-scheme-matrix-and).
- Tang et al., “LogLite: Lightweight Plug-and-Play Streaming Log Compression,” accepted VLDB 2025: [arXiv:2507.10337](https://arxiv.org/abs/2507.10337).
- Shan et al., “LogFold: Compressing Logs with Structured Tokens and Hybrid Encoding,” ICSE 2026: [arXiv:2603.20618](https://arxiv.org/abs/2603.20618), [DOI](https://doi.org/10.1145/3744916.3787801).
- Maveli, Vergari & Cohen, “Can LLMs Compress (and Decompress)?,” Findings ACL 2026: [arXiv:2601.13398](https://arxiv.org/abs/2601.13398). It measures exact round-trip consistency and reports persistent bidirectional failures, including simple bijections.
- Rinberg et al., “Haiku to Opus in Just 10 bits,” 2026: [arXiv:2604.02343](https://arxiv.org/abs/2604.02343). Its lossless setting uses matched LLM/adapters for arithmetic coding; its interactive QA/rewrite setting is lossy.
- Trukhina & Vashkelis, “SemanticZip,” May 2026 preprint: [arXiv:2605.24541](https://arxiv.org/abs/2605.24541). Explicitly lossy and therefore not an exact-codec competitor.
- Mao, Pirk & Xue, “LLMZip: Lossless Text Compression Using Large Language Models,” ICLR 2024 submission: [OpenReview PDF](https://openreview.net/pdf?id=jhCzPwcVbG). It depends on the shared LLaMA2-7B predictor and arithmetic coding; its side-information experiment gives both ends the summary.

## Bounded audit of recent AI-mathematics claims (as of 2026-10-31)

This is a source-and-scope audit, not an independent mathematical proof review. A Lean kernel check can establish that a formal proof derives the encoded statement from its imports and allowed axioms; by itself it does **not** establish that the formal statement matches the intended paper, that the theorem is new, that the proof search was autonomous, or that the result has practical consequences.

- **A result with substantial external mathematical corroboration: unit-distance conjecture.** OpenAI's May 20 announcement links its model-generated proof and a companion paper. The companion arXiv note by Alon, Bloom, Gowers, Litt, Sawin, Shankar, Tsimerman, Wang, and Wood explicitly calls its version “human-verified”; this is materially stronger than relying on the lab announcement alone. The corrected claim is that for infinitely many n there are configurations with at least n^(1+δ) unit distances for a fixed δ>0; the initial argument did not give explicit δ, and a refinement described in the announcement permits δ=0.014. This supports the mathematical construction as human-checked, not an independently reproducible audit of the model's hidden reasoning trace. Sources: [OpenAI](https://openai.com/index/model-disproves-discrete-geometry-conjecture/), [companion arXiv paper](https://arxiv.org/abs/2605.20695).
- **AlphaProof Nexus.** The peer-reviewed Science article reports 9/353 formalized Erdős problems and 44/492 selected OEIS conjectures, and public Lean/natural-language proof files exist. An independent public GitHub issue reports re-running ten Erdős proofs (including a corrected statement) through Comparator, Lean, and nanoda, while also flagging semantic/novelty issues in several OEIS items and a public-artifact count of 38 rather than the paper's 44. The paper itself notes that Erdős #846 also follows from a Reiher–Rödl–Sales projection argument. These points do not invalidate the checked formal proofs; they narrow claims about “newly solved,” statement correspondence, and full reproducibility. We did not run their Lean builds. Sources: [Science](https://www.science.org/doi/10.1126/science.aej2213), [results repo](https://github.com/google-deepmind/alphaproof-nexus-results), [independent replay / issue #4](https://github.com/google-deepmind/alphaproof-nexus-results/issues/4), [paper](https://arxiv.org/html/2605.22763v1).
- **OpenAI ETH claim.** The official October 26 post presents the result as Lean-verified and says an external group led by Impagliazzo, Paturi, and Williams will examine and explain it; OpenAI's post does not claim their participation is endorsement. The public OpenAI scope note says Lean proves exact counting for canonical k-CNF inputs with time exponent proportional to n(log log n)^2/sqrt(log n), while the October 25 manuscript states a sharper n log log n/sqrt(log n) exponent. Both are subexponential, but they are different formal scopes. The theorem would refute ETH if the statement correspondence and proof stand; it would not prove P=NP or supply a practical SAT solver. The public artifacts are available; we did not build them or independently verify the mathematics, and the external examination had not published a verdict in sources checked for this report. Sources: [OpenAI announcement](https://openai.com/index/building-scientific-understanding-with-academic-communities/), [Lean scope note](https://github.com/openai/math/blob/main/lean/docs/378.md).
- **Anthropic ETH claim.** Anthropic's public README gives a reproducible Lake/Lean/Comparator path, pinned Lean/Mathlib versions, and a reported build budget of ~8 minutes on 24 vCPUs/~7 GB peak. It explicitly warns that no machine checks the paper-to-Lean-statement correspondence; it supplies a short statement file for human comparison and lists differences between paper and Lean forms. It also says the asymptotic theorem says nothing about practical SAT instances. We did not build this project or independently inspect the proof. A second lab's independently described proof increases material available for scrutiny; it is not a substitute for independent acceptance. Source: [Anthropic formal-math README](https://github.com/anthropics/formal-math/blob/main/eth/README.md).
- **OpenAI local smoothing / QCD and the Axiom CFSG announcement.** OpenAI publicly links a local-smoothing writeup and Lean file but we found no external expert report on that result in this bounded check. The OpenAI announcement says physics collaborators are withholding QCD/Yang–Mills artifacts while writing them up, so the result cannot be independently checked from the announcement. Axiom's public CFSG README says a sorry-free Lean 4.35.0-rc3 formalization follows the TauCeti statement and that the build was brought under 24 hours using open Lake changes/optimizations; we verified that the GitHub repository and README exist, but did not build it or verify theorem correspondence/project metrics independently. Sources: [OpenAI announcement](https://openai.com/index/building-scientific-understanding-with-academic-communities/), [Axiom CFSG repository](https://github.com/AxiomMath/CFSG).

**Audit verdict:** evidence quality varies claim-by-claim. Some headline results have public proof artifacts; at least one has a human-verified explanatory paper, and AlphaProof has a reported independent replay. Others remain lab claims under examination or are inaccessible. Compilation, statement matching, novelty/priority, and practical consequences are separate gates. No broad conclusion that “AI has proved mathematics” is justified by this bounded survey, and no claim that X66's codecs involved AI theorem proving is implied.

## Leaders and time/CPU accounting

New local leader entries: on the X66 MIT JSON and Apache-2.0 JSON full-gate fixtures, SYNKRISIS leads the measured TAGSTACK runtime-parent-plus-SIBLING scope at 949 and 3,010 tokens, respectively. X66 is exact but rejected and does not change either leader. These are not registry-wide or cross-fixture rankings.

Wall time was 323,693 ms for MIT and 747,369 ms for Apache. Each shell invocation had an 1,800-second timeout; there was no separate CPU quota or wrapper-wide parent-search timeout. The local transform has an 80,000 UTF-16-unit cap and linear JSON scan/transform plus bounded marker-pool selection; the parent tournament is the dominant cost. The X61 repeat took 91,210 ms. Timings are individual observations, not speedup evidence.

## Verdict

X66 meets the mandatory implementation, exact restoration, in-band contract, and tests requirement. It produces no practical Pareto gain on the two complete fixtures measured; both candidates lose and fall back exactly. Keep the registry codec guarded, with the negative results visible. Do not describe it as globally novel, as a frontier winner, as native-LLM decoded, or as a general JSON compression improvement.
