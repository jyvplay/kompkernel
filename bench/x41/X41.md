# X41 — SYSTOLE (συστολή, “a drawing together, a contraction”)

Registry index **31**. `src/lib/omega/systole.ts`. Wraps PERITROPE (30).

Removes the **separators inside structured numbers** and restores them by template.
The first mechanism in this stack that pays for a removal **without repetition**.

---

## A. Formal model of the mechanism

**Admissible objects.** A *structured numeric run*: a maximal run of the form
`D⁺ (s D⁺)⁺` where `D` is a digit and `s ∈ {'.', ':', ';', '-'}`. Its *shape* is the
sequence of digit-group sizes with the literal separators between them
(`2026-09-30` → `4-2-2`). Its *digit count* is the total number of digits.

**Transform.** For a set `T` of shapes, delete every separator inside every run whose
shape is in `T`.

**Inverse.** The reader identifies a stripped run by its digit count, looks up the
shape, and re-inserts separators positionally.

**Information/access model.** The reader is a bare LLM with one chat message
(contract + wire). No system prompt, no tools, no skills file. The reader must be able
to do the inverse **by counting to a position inside a short digit string**.

**Resource counted.** `o200k_base` tokens of the whole message.

**Success.** `decode(encode(x)) == x` byte for byte, **and** `|encode(x)| < |parent(x)|`.

**Quantifier order.** For every document `x`, for the shipped template set `T`:
(1) `systoleUndo(systoleApply(x,T),T) == x`; (2) every maximal digit run in
`systoleApply(x,T)` whose length is a shipped digit count was produced by this
transform; (3) total message tokens strictly below the parent. All three are checked
in-process, not argued.

**Regime.** Separators worth removing: 3–14 digits per template (below 3 there is
nothing to count, above 14 the reader cannot count). `,` excluded.

## E. Three constraints, all chosen for the reader

### E.1 Width cap ≤ 14 digits — justified by measurement, not by taste

Restoring a separator means counting to a position. **arXiv 2605.02028** (Dai et al.)
queried **126 leading model variants** with a stable counting assay and found that
**every one** has a finite counting capacity (CC) far below its nominal context length,
with failures clustering on round numbers. Context access does not imply procedural
state maintenance.

This is why the largest single measurement of the turn is refused. Treating `,` as a
separator merges an entire CSV row into one template and shows **−1,512 raw on vix** —
but the stripped form is a forty-digit blob. Refused on principle.

**CharBench (arXiv 2508.02591)** measures the same tradeoff from the other side: for
tasks requiring a model to locate a character, accuracy declines as the containing
token grows — *a tradeoff between token-level compression and the ability to reason
about character-level structure*. That is the bound every transform here lives under.

### E.2 One template per digit count

The reader identifies a stripped run **by its length**. On vix, dates (`4-2-2`) and
prices (`2.6`) both strip to eight digits. Only one ships: the prices, at 504
occurrences against 126. The 378 the dates would have paid is forgone **to keep the
instruction unambiguous**.

### E.3 Mechanical invertibility + unambiguity

Both guards caught real failures in a naive version:

| lane | naive restore produced | truth |
|---|---|---|
| find-listing | `11:35:25` | `113525` (a size column) |
| dump.sql | `0000-00-00` | `00000000b09b3a13…` (hex in `decode(...)`) |
| chart.svg | `8.00 4.00` | `800 400` |
| email-thread | `20:26 … -04:00` | `2026 … -0400` |

## F. Two corrections to template selection

Both were found by watching a naive version lose most of the gain.

**Ambiguity is not monotone in the template set.** On aapl, `4-2-2` is ambiguous **on
its own** (the decimal part of `77.44539475` survives as a native 8-digit run) but
perfectly readable **once `2.8` ships too** (that run becomes part of a 10-digit one).
A single best-first pass: **201 of 915**. Iterating to a fixed point: **915**.

**A weak template must not claim a slot a stronger one is still reaching for.**
`2.6` (8 digits, 6 raw) took the 8-digit slot in pass 1 while `4-2-2` (8 digits, 720
raw) waited for its second chance.

## H. Honest citation — including the part that cuts against this

**The rule it exploits is documented elsewhere, in the opposite direction.**

* A 2026 analysis (dev.to, ji_ai) confirms `\p{N}{1,3}` in cl100k_base and o200k_base
  and shows chunking runs **left to right**, so boundaries depend on a number's *total
  length* rather than on place value; a thousands separator is a **hard token boundary**
  forcing right-to-left power-of-1000 alignment.
* **Singh & Strouse, arXiv 2402.14903**: comma-separating numbers at inference
  materially improves arithmetic; under length mismatch, left-to-right tokenization
  collapses to **8.25 %** accuracy, with a stereotyped "digit 4" error.

**Both are arguments for ADDING separators so a model can compute.** SYSTOLE removes
them, because the objective here is the token count of the *message*, not arithmetic the
model might later perform on it. **Those objectives genuinely conflict: a wire produced
by this codec is a worse substrate for downstream mental arithmetic than the original.**
That is a real cost the token count does not see.

* **Arcee Trinity Large, arXiv 2602.17004 §2.1.1** adopted place-aligned chunking
  following Singh & Strouse, and reported that the natural zero-width lookahead regex
  `(?=(\d{3})+(?!\d))` suffers **catastrophic backtracking on long digit strings**,
  spiking tokenization to minutes; they replaced it with a three-stage pipeline. This is
  a caution about the same regex machinery, which is why the run scanner here trims and
  resumes rather than using nested lookarounds.
* **arXiv 2601.14658**: modern subword tokenizers produce **non-unique encodings** —
  multiple token-id sequences detokenize to the same surface string. A standing caution
  for a stack whose entire accounting is done in tokens.
* **arXiv 2510.06824**, **arXiv 2502.09741 (FoNE)**, **arXiv 2601.09706**: numeracy
  work confirming that digit splitting is the bottleneck for number handling.
* **arXiv 2605.00817**: first-answer accuracy falls from 63 % at 5 procedural steps to
  20 % at 95 — directly relevant to how many template restorations can be asked of one
  message.

## I. Greedy / non-greedy, and the bound

* **Greedy: NO** for template selection — every template is priced on the real token
  count of the text it produces, and every surviving set is re-verified for exact
  invertibility and reader-unambiguity. **NO** for the parent gate — the full message is
  encoded twice and the worse discarded. It *is* a greedy set cover in one respect:
  templates are considered in order of measured saving and the fixed point is reached by
  repeated passes, not by search over all subsets.
* **Time / CPU bound: YES.** Detection is one regex pass plus one tokenization per
  candidate shape. The gate needs a **second full PERITROPE encode** of the contracted
  text, so encode time roughly doubles where viable: **289 s aapl, 705 s vix**. A
  raw-saving pre-filter (`SYSTOLE_MIN_RAW = 20`) skips the second encode wherever it
  cannot pay — which is most lanes.

## J. Honest size

43 on aapl, 29 on vix, 4 on bibliography, 1 on meeting-transcript; zero on the other
thirteen. A narrow mechanism for high-entropy numeric columns. **It barely touches prose:**
bibliography and meeting-transcript are the only prose-adjacent lanes that move, by four
tokens and one, and the diagnostic says why with a number — kb-article contains one
structured numeric run in the entire file, prose-01 two, together worth three tokens.
