# Z10 — AMPHORA (DAEDALUS ∥ CHIRON exact-gated minimum), honest result

Branch `arena/da2b9818-kompkernel`. Codec registered: `amphora` (`src/lib/omega/amphora.ts`, registry key `amphora`).

**Bottom line.** AMPHORA is exact and never worse than DAEDALUS on the 55 documents measured. It gains on
2 of 55: micromatch/README.md (10,846 → 6,859 one-chat tokens, −36.8%) and bench/holdout-lang/ja-kb.txt (655 → 575, −12.2%).
It does **not** meet the general-gain bar. On eight other long English prose documents it returns DAEDALUS's output exactly.
The gain is narrow and rests on one document. On the probed documents, wall time is the sum of both arms: about 1.5–2× DAEDALUS alone (`cvd.jsonl`).

- The one-chat token counts are real `o200k_base` counts (`src/lib/omega/bpe.ts`).
- Context budget: I have no tool that reports this conversation's token usage or the remaining context. I cannot give

## 1. Formal model (A)

- **Objects:** text `d` (UTF-8), codec `E(d) = (wire, contract)`, reader `R` = one bare chat turn, no system prompt.
- **Access:** encoder may call the tokenizer offline. It may not call a model.
- **Resource:** o200k tokens of the whole message (contract + wire).
- **Success:** `∃C. (∀d∈D: exact(C,d) ∧ M(C,d) ≤ M(incumbent,d)) ∧ (∃d∈D: Δ ≫ few tokens) ∧ general(C)`.
  `general(C)` means the gain holds across document classes, not one document. The third clause is the one that fails.
- **Boundary:** AMPHORA changes nothing on 53 of 55 documents and gains on 2. It is not general.
- **Not substituted:** lossy compression; a Rosetta-mode codec (out of scope by instruction); wire-only counts; raw-baseline
  counts (the baseline is the incumbent, DAEDALUS).

## 3. Mechanism portfolio and why AMPHORA is the only shipped candidate

Six mechanisms were considered. Only one was built and measured end to end. The rest are unmeasured or dead:

1. **Deterministic DAEDALUS (work units).** Measured dead: DAEDALUS's output does not depend on budget on the 4 long docs.
2. **CHIRON fallback when DAEDALUS predicts identity (AMPHORA).** Built. Narrow gain (micromatch −37%, ja-kb −12%); zero on 8 others.
3. **Transliteration of non-English prose.** Measured dead (ru-kb +61%).
4. **Span-limited ARIADNE → full-span search.** Hypothesis, unmeasured as a new codec. The micromatch evidence is consistent
   with ARIADNE's span limit, but I did not verify the cause. CHIRON already covers this span range.
5. **Reference-link-heavy markdown class.** Unmeasured. micromatch has many link reference lines. A class test needs ≥ 10 such
   documents, which I did not find in the repo.
6. **Learned or cheap predictor for "CHIRON pays".** Unmeasured. Would need more labelled documents than the 55 measured.

## 4. Second-order adversary (G) on AMPHORA

- **A1, selector hides a worse winner:** the min is over exact candidates only, so no decode failure can win. Checked:
  47/47 exact on the holdout run and 8/8 on the long run; the wire decodes with both `chironDecode` and CPython.
- **A2, DAEDALUS non-determinism changes winners:** possible. The DAEDALUS arm is wall-clock budgeted, so the chosen
  winner can differ by machine load (the 0.5% swing above). The CHIRON arm is deterministic (KAIROS 32M work units).
- **A3, tie or identity edge cases:** if no candidate beats identity, the output is identity. In the 55-document run, 9 documents returned identity, and each round-trips.
- **A4, latency attack:** the runtime is the sum of both arms. Measured across the 55-document run: 0.1–85 s per document (`ms` field). On the probed documents the CHIRON arm alone took 21–24 s and DAEDALUS took 36–62 s (`cvd.jsonl`).
  An attacker can force the slow path on any document. This is a real cost, not a bug.
- **A5, two-arm tournament:** the user prefers non-tournament paths. AMPHORA is a tournament of two exact encoders. It is
  labelled that way in the code and here.
- **A6, reader contract:** both arms emit CHIRON-family wires, so the contract is shared. No new contract. Native LLM
  readability remains unverified (see §0).

## 6. What did we miss (Q)

- **The gain is in the selector, not the grammar.** CHIRON already has the mechanism. DAEDALUS's predicted arm skips it on
  some long prose. Measured on one document. Generalization is not shown.
- **The "frontier" depends on which leaders count.** AETHER, HARMONIA, and PANACEA report 7,350 wire tokens on micromatch. That is a wire count, not a one-chat count, and their mode uses Rosetta, so I did not compare them. Excluding Rosetta, the best measured one-chat result there is CHIRON's 6,859 (not a frontier claim over all 130 codecs; the full registry was not run).
- **Latency is a metric we have not optimized.** Every codec here is 20–80 s per 10k-token document. A user-facing
  codec should report time as well as tokens.
- **Measured per-lane headroom is near zero for short prose and kb-scale text.** The gap is in long, structured, or
  reference-heavy text, which the holdout (≤ 4 KB) under-represents.
