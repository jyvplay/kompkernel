# X46 — BIFRONT: right-boundary path factoring, measured and rejected

**Date:** 2026-10-26 (local). **Branch:** `arena/1ac6de8e-kompkernel`.
**Implementation:** `src/lib/omega/bifront.ts`; registry key `bifront`.
**Measured parent:** SYNKRISIS X45. **Metric:** `M = countTokens(complete contract + LF + wire, o200k_base)`; the full one-chat message is charged, with no system prompt, skills file, hidden decoder table, or external decoder.

## Executive verdict

BIFRONT is a real, registered codec implementation, not an analysis-only proposal. Its deterministic transform factors the longest common suffix from final path fields, states the literal suffix in the in-band English contract, then asks SYNKRISIS to encode the transformed text. It returns the candidate only after the repository's exactness checks and only if the complete message is strictly smaller than SYNKRISIS X45; otherwise it returns the parent message unchanged.

The mechanism is exact under the TypeScript oracle and the 29-case red team passes, including 16 negative-space cases and an explicit modal-shortcut falsification. The final TypeScript check passes. The post-optimization 16-lane and 19-lane comparisons are both exact and no-regression against the same stored SYNKRISIS X45 result, but have **zero strict wins**. Sums are 6,740 → 6,740 on the 16-lane set and 5,696 → 5,696 on the 19-lane comparison. The eligible `find-listing` candidate was rejected: the post-optimization full candidate is 1,281 tokens against a 1,267-token parent; the current returned message is the parent's 1,267-token message.

This is not a meaningful Pareto improvement. The output-token axis ties on every measured lane, while BIFRONT adds a second expensive parent encode for eligible inputs. Under `OMEGA_DET=1`, the current `find-listing` lane took 121.249 seconds. There is no everyday prose or ops win. The X39 frontier subset is still only 16/17, with 14 lanes untested. **X46 therefore does not pass the requested success criterion.** The implementation is retained as a measured negative, not advertised as a successful compression advance.

## 1. Mechanism and full-message contract

For a homogeneous path-list-shaped source, BIFRONT:

1. parses each nonempty line's final non-space field as a path if that field contains `/` or `\\`;
2. computes the longest suffix shared by all such paths, in Unicode code points;
3. removes that exact suffix from every final path field, preserving the rest of each line and its exact line ending; and
4. appends a natural-language instruction containing the JSON-quoted suffix to the SYNKRISIS parent contract.

The candidate's in-band rule is of the form: `After decoding the parent, append ".js" to every final path field. Print only.` The literal suffix is data carried in the same message, not a presumed extension or a hidden table. The wire is SYNKRISIS on the transformed source. BIFRONT does not ask the reader to retrieve a corpus-specific dictionary or to call an external program.

This is a *right-boundary* factor, unlike DENDRON's shared leading path segments. It is still a standard string-differencing family, not a claim of a new compression primitive. The differentiator under test is the in-band, one-chat contract and its measured full-message gate.

## 2. Formal model, exactness, and quantifier order

### 2.1 Domain and transform

Let `D` be valid UTF-8 text represented as a JavaScript string. Let `P(x)` be the complete SYNKRISIS X45 message on source `x`, and `D_P` its contract-directed decoder. Define the eligible BIFRONT domain `D_B ⊆ D` by the bounds and row-shape conditions in §3.

For `x ∈ D_B`, the planner chooses the maximal shared suffix `s(x)` and forms `T_s(x)` by deleting precisely that suffix from each final path field. The inverse `R_s` appends the exact same `s` to every final path field. The line mapper preserves `LF`, `CRLF`, bare `CR`, blank lines, field prefixes, tabs, and trailing spaces. The planner is accepted only when its local inverse satisfies

```text
R_s(T_s(x)) = x.
```

Let `C(x)` be SYNKRISIS's complete contract-plus-wire message on `T_s(x)`, with the suffix rule appended to the parent contract. Let `M(m)` be the exact `o200k_base` token count of the complete message `m`, not the wire alone.

### 2.2 Encoder and decoder relation

For a candidate message, the intended direct reader is

```text
D_B(C(x)) = R_s(D_P(C_parent(x)))
           = R_s(T_s(x))
           = x,
```

where the suffix `s` is read literally from the in-band contract. For an identity/fallback message, the reader follows SYNKRISIS unchanged. The implementation also checks `candidate.decoded === T_s(x)` and a final `R_s(candidate.decoded) === x` before considering emission.

The selection order is important:

```text
for each x:
  compute the exact SYNKRISIS result P(x)
  if the parent does not report exactness: return raw identity
  if x is outside D_B: return P(x)
  compute SYNKRISIS on T_s(x)
  if candidate decode or R_s check fails: return P(x)
  count the whole C(x) under o200k_base
  if M(C(x)) >= M(P(x)): return P(x)
  otherwise emit C(x)
```

Thus the implementation's conditional guarantee is

```text
∀x for which SYNKRISIS is exact:
    D_B(B(x)) = x  and  M(B(x)) ≤ M(P(x)).
```

The candidate is emitted only under the stronger condition `M(C(x)) < M(P(x))`. These are different quantifiers: an exact, no-regression wrapper does **not** imply that a strict win exists. In the measured suites, the existential strict-win claim is false: no input has a recorded strict BIFRONT win. If the parent itself fails its exactness field, the wrapper uses raw identity; the measured no-regression statement below is based on lanes where the named parent is exact.

This is an executable, end-to-end equality check, not a Lean-checked universal theorem. Equality is exact for the repository's decoded text inputs; arbitrary binary data and invalid UTF-8 byte streams are outside the codec's text domain.

## 3. Source, parameter, and boundary conditions

The planner is deliberately conservative:

- nonempty input of at most 50,000 JavaScript characters;
- at most 2,000 split line bodies;
- at least four nonempty path rows;
- every nonempty row must end in a path field; a multi-field row must have a space or tab separator before that field;
- path fields must contain `/` or `\\`; a bare filename without either separator is not considered a path;
- the maximal common suffix must contain 2–64 Unicode code points;
- removing it must leave a nonempty residual in every path;
- mixed ordinary prose rows, suffix outliers, and rows that would be emptied reject the transform;
- no Unicode normalization, case folding, line-ending normalization, or extension inference is performed.

The 64-code-point suffix, 50,000-character input and 2,000-line bounds are implementation caps, not claims that larger cases are mathematically impossible. `bifrontRestore` fails closed on an empty/newline suffix or malformed transformed rows.

## 6. Negative space and modal-shortcut falsification

The red team is `bench/x46/redteam.ts`; its machine-readable result is `bench/x46/receipts/redteam.json`. **29/29 passed**, with **16 explicit negative-space cases**. The negative set includes:

1. only three rows;
2. one-character common suffix;
3. mixed `.ts` and `.js` where only a one-character tail remains;
4. an ordinary prose row among paths;
5. a path earlier in the row but a non-path final field;
6. bare filenames with no slash or backslash;
7. every path equal to the suffix (empty residual forbidden);
8. a 65-code-point suffix beyond the cap;
9. more than 2,000 line bodies;
10. empty input;
11. input beyond the character cap;
12. a shared suffix that would empty one path;
13. no common terminal suffix;
14. one suffix-outlier row;
15. ordinary-word final fields rather than path fields; and
16. malformed transformed input, which must fail closed.

The mandatory **modal-shortcut falsification** is test 29: four `.js` paths and four `.jsx` paths produce the same transformed path body under different suffix parameters. A reader that silently assumes the familiar `.js` suffix returns the wrong source for the `.jsx` case. Both explicit parameters round-trip, and the wrong parameter is rejected. This is a deterministic string test, not evidence that a language model will obey the parameter.

Positive controls additionally cover blank paragraphs, CRLF, final LF, trailing spaces, tab-separated prefixes, Windows backslash paths, Unicode paths, punctuation/quotes in the suffix, and a 46,000-character divergent-prefix stress case. The stress case motivated the suffix-scan repair described next.

## 7. Structure-specific second-order attacks and repair re-gates

| Attack | Failure mode | Repair / re-gate |
|---|---|---|
| **Quadratic suffix checking on long divergent prefixes** | A path-list heuristic can repeatedly compare a long prefix even when the common tail is short. | Replaced the repeated suffix test with a reverse Unicode-code-point scan whose work is bounded by the total path lengths. Added the 46,000-character divergent-prefix red-team case. It passes; final TypeScript check and the 16-/19-lane no-regression suites were rerun afterward. |
| **Modal extension guessing** | `.js` is common, but `.jsx` can have the same transformed path body when the removed tail is guessed rather than transmitted. | JSON-quote the exact suffix in the in-band parent contract; test 29 proves a wrong parameter is not accepted by the structural inverse. No model behavior is inferred from this oracle. |
| **Mixed record types / suffix outlier** | Appending the suffix to a prose row or to one exceptional path corrupts data. | Planner refuses any nonempty non-path row and computes a suffix common to every accepted path. Negative cases 6, 7, 24–26 and the mixed-row tests re-gate it. |
| **Empty residual / over-stripping** | A path equal to the suffix would disappear, and a reader might not know whether it was an empty path or a missing field. | Require nonempty residual for every path; red-team cases 9 and 23 pass by refusing the plan. |
| **Line endings and whitespace** | Rebuilding lines with a canonical newline or trimming trailing spaces changes bytes. | Map line bodies while preserving captured `LF`, `CRLF`, bare `CR`, prefix, trailing spaces and tabs. Positive controls 10–17 pass. |
| **Untrusted/prompt-like path text** | A filename suffix can contain quotes or natural-language-looking text. JSON quoting preserves the literal for a normal parser but cannot prove that an LLM will treat all such text as inert data. | Quotes/punctuation are tested structurally, but prompt-injection semantics were not tested with a model and remain an explicit LLM-readability risk. The parent gate cannot repair model interpretation. |
| **Unicode normalization or confusable characters** | A reader may normalize code points or silently substitute a visually similar path. | The implementation performs no normalization and checks exact strings. No LLM trial was available; visual/semantic normalization is unverified. |

The two actual repairs that affect the committed implementation—linear suffix scanning and explicit parameter transmission—were re-gated by the stress/modal tests, TypeScript, and both complete-parent comparison runs. Prompt-injection and cross-model exactness are not claimed as repaired.

## 9. Time versus token Pareto analysis

The planner itself is linear in total source/path length: it splits the lines, parses final fields, scans the common suffix from the end once per path, and maps line bodies once. It uses O(n) space for line/path arrays and the transformed text. The maximal suffix is a deterministic greedy choice; there is no search over suffix lengths or competing transforms.

That is not the cost of `bifrontEncode`. On an eligible source it runs SYNKRISIS once on the original and again on the transformed source, then recounts the complete candidate. It inherits the parent's production wall-clock search budget per call; it adds no global deadline of its own. In the normal clock configuration the DAEDALUS family is limited by `min(20,000 ms, 1,200 + 1.1 × inputChars)` per parent search. Under `OMEGA_DET=1` that clock is pinned to zero, so the search reaches its natural end; `find-listing` took 121.249 seconds in the post-optimization 16-lane run. These benchmark times are not production latency bounds, and the wrapper can invoke the expensive parent twice.

For the measured set, the token coordinate is tied on every lane and encode work increases on the eligible lane. There is therefore no Pareto point to claim: the BIFRONT message is never smaller, and the measured mode is slower. A purely theoretical time bound for the tokenizer and inherited search was not proven here; the production budget is wall-clock, not a fixed CPU-instruction bound.

## 10. Literature review and adjacent problems

### 10.1 Compression and exact-inversion literature

- [Kalcher, “Frequency-Ordered Tokenization for Better Text Compression,” arXiv:2602.22958v2 (2026)](https://arxiv.org/html/2602.22958v2) reorders pretrained BPE tokens using a fixed frequency table and variable-length byte codes before zlib/xz/brotli/zstd. On enwik8 it reports 1.44–7.96 percentage-point gains and faster standard compression, with the table overhead addressed in the paper. This is substantive byte-stream compression, but it is not a single-chat natural-language decoder: it uses a fixed rank table and ordinary compressors. It is evidence about token/byte economics, not evidence that an LLM can decode BIFRONT.
- [Maveli, Vergari, and Cohen, RTCE, arXiv:2601.13398v2 (2026)](https://arxiv.org/html/2601.13398v2) evaluate exact round-trip inversion across four lossless algorithms, with 250 inputs per algorithm. Their abstract reports that zero-shot prompting, trace-supervised fine-tuning, and iterative self-reflection did not close the exact-inversion gap, including on RLE. This is adjacent evidence that exact inversion is a real model capability question; it is not a test of BIFRONT or of the current repository's models.
- [Kanda, Morita, and Fuketa (2017), front/back coding for massive string dictionaries](https://kampersanda.github.io/pdf/InnovateData2017.pdf), and [Ferragina, Rotundo, and Vinciguerra (2025), “Two-level massive string dictionaries”](https://www.sciencedirect.com/science/article/pii/S0306437924001480) are directly adjacent: sorted strings can be represented with shared prefixes/suffixes or rear coding. BIFRONT does not claim novelty for common-suffix or rear coding. These works concern algorithmic dictionaries and normal decoders, not a one-chat, no-hidden-table LLM contract.
- [VCDIFF, RFC 3284](https://www.rfc-editor.org/rfc/rfc3284.html) is broader byte-delta prior art. BIFRONT is a restricted path-row factor, not a new general delta method.

The adjacent problems must not be conflated: conventional byte compression optimizes bits and may rely on fixed tables; a data-structure dictionary may use shared state; LLM-native decompression requires a model to infer the exact inverse from one visible message; this repository's TypeScript equality check proves only the last thing about the code's own reader, not about an LLM. RTCE measures a related model property but does not validate this format.

- **KLS collaboration.** Claude Fable 5 and Fable 5.1 are two of four named tools in Song–Zhang's KLS disclosure below. That does not make the KLS proof an Anthropic-only result: the authors name four tools and describe a human-directed research process.

#### Google DeepMind / Gemini

- **Aletheia.** Feng, Trinh, Bingham, Hwang, and coauthors' [“Towards Autonomous Mathematics Research,” arXiv:2602.10177v1](https://arxiv.org/html/2602.10177v1) describes Aletheia as powered by an advanced Gemini Deep Think system with extensive web/tool use. The paper distinguishes an AI-generated arithmetic-geometry eigenweights paper with no human intervention, a human–AI independent-set bounds paper, and a 700-question Erdős evaluation that reports four new solutions with semi-autonomous AI and human checking. Those are different autonomy levels in the authors' own taxonomy, not one undifferentiated “Gemini proved mathematics” claim.
- **AlphaProof Nexus.** Tsoukalas et al.'s [Science paper](https://www.science.org/doi/10.1126/science.aej2213) describes an LLM proof-generation loop with Lean verification and reports 9/353 formalized open Erdős problems and 44/492 selected OEIS conjectures, plus research results in other areas. A contributor's [issue in the public results repository](https://github.com/google-deepmind/alphaproof-nexus-results/issues/4), prepared with Claude Code, reports replaying all published Erdős proofs plus corrected #741(i) through Lean's kernel and nanoda; it says ten statements passed. The same report flags four OEIS issues: possible multiplicity-versus-distinct-factor mismatch for A382590, earlier results for some listed conjectures, a potentially elementary reduction for A237271 under its encoded characterization, and 38 public repository proofs versus the paper's 44. These are contributor-reported findings, not reproduced here; a kernel-checked proof of an encoded proposition and the novelty/statement fidelity of a database conjecture are separate questions.

#### Microsoft / independent KLS papers

- **Song–Zhang.** Zhao Song and Xinzhi Zhang's [arXiv:2610.01447v2](https://arxiv.org/html/2610.01447v2) claims a dimension-free KLS/Poincaré bound. ### 10.3 Research stopping boundary

The review found peer-reviewed and preprint work, formal artifacts, and detailed disclosures from several organizations. The references above support statements about what the authors, repositories, or third-party issue report; they do not authorize a universal claim that every result is correct, novel, or independently verified.
