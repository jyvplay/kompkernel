### Actual Behavior

On a Panther Lake iGPU, through onnxruntime's OpenVINO execution provider (GPU, OpenCL), the **first inference** of InsightFace `buffalo_l` recognition (`w600k_r50`) faults the GPU **whenever PP-OCRv5 mobile recognition was loaded or run directly before it** in the same process.

The kernel logs a CCS page fault on an unbound user VA, then a CAT error, an engine reset and a job timeout. OpenVINO then returns `CL_OUT_OF_RESOURCES`, and the context stays dead (every later call returns `CL_INVALID_EVENT`).

It is deterministic in a single-threaded script, and swapping the last two inferences makes it pass every time. There is no memory pressure: 9–20 GB `MemAvailable`, sampled every 5 s.

| Sequence | Trials | Faults |
|---|---|---|
| reproduction sequence below | 2 | 2, both at the first face-recognition run |
| same, last two runs swapped | 6 | 0 |
| 27 other orderings without "OCR rec immediately before face rec's first run" | 27 | 0 |
| any order, once every model has run at least once | 20+ | 0 |

Production traces show the same pattern: every one of ~20 faults had OCR recognition (load or run) directly before face recognition's first inference. Threading and concurrency make no difference (tested). Holding the GT awake with debugfs `forcewake_all` doesn't change it either, so it is not RC6.

Things that hold across all ~20 faults:
- **Fault fields:** FaultType 0, AccessType 0, FaultLevel 0, CCS instance 0.
- **Address:** always within `0x0000d556a270b000`–`0x0000d556a5aeb000`, across different processes and ASIDs. That suggests one specific runtime allocation at a predictable VA.
- **Kernel response:** `Fault response: Unsuccessful -EINVAL`. The address was never bound, so this looks like an allocation the runtime submitted work against but did not make resident.
- **Devcoredump:** `VM state` shows `[0].error: -19`, so there is no VM snapshot.

### Expected Behavior

The first inference of a freshly compiled model completes normally, whatever other model ran last in the same process or context. No GPU page fault, no engine reset, and the OpenCL context stays usable.

### Reproduction Rate

Always reproduces - 100%

### Steps to Reproduce

The models are from Hugging Face: `immich-app/PP-OCRv5_mobile` (detection + recognition), `immich-app/buffalo_l` (detection + recognition), `immich-app/ViT-B-32__openai` (visual).

Each one is an onnxruntime session on the OpenVINO EP (`device_type=GPU.0`, FP32, OpenVINO model cache dir set), compiled on first use. One process, one thread, calls strictly sequential:

1. Load OCR detection, face detection, CLIP visual.
2. Run OCR detection, face detection, CLIP visual once each.
3. Load OCR recognition, face recognition.
4. Run OCR recognition.
5. Run face recognition. **This first inference of the model faults the GPU.**

Swap steps 4 and 5 and it passes 6/6.

### Additional Notes

- **Possibly related:** #1010. It has the same `Engine memory CAT error [18]: class=ccs` with a fixed-VA fault on a kernel private surface left unbound after `evictUnusedAllocations()`. The trigger differs: no userptr failure or memory pressure here.
- **Workaround in use:** run each model once right after compiling it (load → run, load → run …), so no model's first inference follows another model's work. It has been fault-free since 2026-10-05 21:38 UTC.
- **Possible second suspect:** the trigger depends on which *other* compiled model ran last. OpenVINO's GPU plugin shares one OpenCL context and memory pool across compiled models, so its buffer reuse could be involved. Happy to cross-file with openvino if you think it belongs there.
