# X65 — FOTAR: frequency-ranked in-band aliases (measured negative)

Date: 2026-10-30. This report records the implementation, exactness checks, full-message measurement, source audit, research review, and speed investigation. Receipts are under `bench/x65/receipts/`.

## Mechanism and contract

FOTAR (Frequency-Ordered Token Aliases) counts repeated multi-character BPE token surfaces, ranks them by a deterministic character-mass proxy, assigns collision-free local aliases, and replaces the selected token surfaces. Its one-message contract carries a JSON array of `[alias,literal-surface]` pairs, then the child parent message. The reader parses that literal table and expands aliases left-to-right, longest alias first; all unlisted characters are copied exactly. No external dictionary is used. The composed candidate is FOTAR → APOGRAPHE. The encoder admits at most 96 entries and refuses unsafe/oversized source text.

The dictionary plan is deterministic and bounded, not a token-space search: the top ranked surfaces are admitted in fixed order. Character mass is only a planning heuristic. Emission requires byte-exact expansion and a strictly cheaper *complete in-band message* than the same-source TAGSTACK runtime-parent frontier plus SIBLING-TEMPLATE. Otherwise the exact frontier winner is returned.

The implementation now constructs the final map once and counts its FOTAR-only message once. The earlier implementation rebuilt and token-counted each prefix of the dictionary (up to 97 render/count passes); this was needless work because the admission order is fixed and no intermediate plan can be emitted. This is a decision-preserving optimization. No wall-clock speedup is claimed from it.

## Exactness and measured outcome

- TypeScript red team: 12/12 checks pass, including Unicode/astral characters, line endings, marker collisions, longest-marker parsing, serialized-envelope parsing, table-derived round trip, and malformed JSON refusal (`fotar-redteam.json`).
- Separate stdlib-Python twin reconstructs the table from serialized `tableJson` and restores its 919-codepoint Unicode control byte-for-byte (`fotar-twin.json`). These check the alias layer, not an independently reconstructed APOGRAPHE decoder.
- Real OpenStack log fixture: `bench/holdout-ops/openstack-loghub-26.log`, SHA-256 `55899f656f979de1bfae393eeb27a9a25f0c7c13d6b1da1118a61d80c8d54a7e`, 7,969 characters, 4,028 raw o200k tokens. The planner selected 7 entries used 88 times and mapped 7,676 characters. Standalone FOTAR contract+table+payload cost 4,836 tokens. The exact composed APOGRAPHE candidate cost 1,080 tokens. Two full-gate runs, both with the same source SHA and unset `OMEGA_DET`, completed the source frontier at 896 (`synkrisis`) and 885 (`diastema`), respectively. The final rerun after the planner optimization returned the 885-token frontier; FOTAR was refused and that exact message returned. The candidate loses 195 tokens on the final run (184 on the earlier run), not a Pareto gain. The two runs took 511,910 ms and 570,388 ms and selected different winners, so the production-time frontier is runtime-sensitive. Latest receipt: `fotar-fullgate.json`.
- Screening (direct FOTAR contract+table+payload only, before parent composition): prose changelog 15,675 vs 10,906 raw tokens; file listing 6,730 vs 3,997; OpenStack log 4,836 vs 4,028; `metrics.tsv` had no plan. These are preflight screens, not full-frontier comparisons. Receipt: `fotar-screen.json`.
- No new fixture-specific leader or Pareto win is established. The previous X61 frontier repeat remains 210 tokens, `akolouthia2`, exact and complete; this run matches the previous gate. Full setup/receipt: `bench/x61/receipts/frontier-repeat-x61.json`.

## Verification boundary

The FOTAR table parser/inverse is now independent of encoder-side dictionary metadata: it parses the literal JSON envelope, then uses the serialized table to expand a decoded parent payload. In the composed full-gate check, however, APOGRAPHE parent restoration still uses `apographeDecodeResult(child)` and thus result metadata. We did not reconstruct every APOGRAPHE/underlying-parent option from the candidate message alone, and did not test decoding by a native LLM. The format is stated in-band and human-readable; native LLM decoding is unverified and not claimed.

## Prior art and novelty boundary

The mechanism is ordinary dictionary coding over repeated tokenizer surfaces with an in-band table, closely related to this repository's VERITAS/PHALANX dictionary family; it is not a globally novel compression algorithm. Prior art includes *Lossless Prompt Compression via Dictionary-Encoding and In-Context Learning* ([arXiv:2604.13066](https://arxiv.org/html/2604.13066)), which charges dictionary tokens in its objective but places the dictionary in the system prompt in its experiment. That setup does not establish the requested single-message contract. FOTAR explicitly puts its table in the same message, and the real full-message test loses to the stack frontier. No novelty or Pareto claim is made.

## Speed investigation, with fidelity held fixed

Two observations are separate and must not be combined into a general speed claim:

1. FOTAR's planner was changed to avoid repeated prefix reconstruction and token counting. The candidate ordering, final entries, and final message are unchanged by construction; red-team and full-gate exactness were rerun. This reduces redundant work, but no before/after timing series was collected.
2. REPRISE (X64) is a bounded, encoder-side memo of previously accepted exact TAGSTACK results. It returns the same complete message; it cannot reduce cold-call time or message size. Its one recorded cold/warm observation was 136,733.854 ms vs 0.129 ms for a same-process repeat of the 1,203-character `metrics.tsv` input. The fresh X61 setup repeat in this session matched the prior 210-token `akolouthia2` result at 113,300 ms vs the previous 94,136 ms; elapsed time varied, so this is no speedup evidence. See `src/lib/omega/reprise.ts`, `bench/x64/receipts/reprise-cache.json`, and `bench/x61/receipts/frontier-repeat-x61.json`.

## Live research review: AI mathematics (bounded, not an exhaustive survey)

Primary artifacts were inspected on 2026-10-30. The important distinction is between (a) a proof checker validating a formal theorem, (b) the formal statement matching a paper's intended theorem, and (c) the mathematical result being new. They are different claims.

- **OpenAI — recent formalized results.** The public [OpenAI math repository](https://github.com/openai/math) includes formal statements and per-result scope notes. Its [ETH note, `378.md`](https://github.com/openai/math/blob/main/lean/docs/378.md), says Lean proves a fixed-`k` counting/SAT result for canonical inputs, while the October 25 manuscript states a sharper bound. The checked formal scope is therefore not identical to the paper's strongest headline bound. This is a scope distinction, not a judgment on the mathematical proof. The note for [smooth local isometric-immersion obstruction, `334.md`](https://github.com/openai/math/blob/main/lean/docs/334.md) states a specific counterexample metric and local scope. The public artifacts are inspectable, but we did not build the repository or obtain an independent expert review of these results in this task.
- **Anthropic — claimed ETH refutation.** Its [formalization README](https://github.com/anthropics/formal-math/blob/main/eth/README.md), [`MainResults.lean`](https://github.com/anthropics/formal-math/blob/main/eth/MainResults.lean), and [`comparator.json`](https://github.com/anthropics/formal-math/blob/main/eth/comparator.json) expose the theorem statements, solution, permitted standard axioms, and a Comparator/nanoda check path. The README explicitly says no machine checks that the Lean statements faithfully match the paper; it describes a short statement for human comparison. The documented full build takes about eight minutes on 24 virtual CPUs and 7 GB peak for the cited process. We inspected the artifacts but did not run that build or independently audit the mathematics.
- **Google DeepMind — AlphaProof Nexus.** The [paper](https://arxiv.org/html/2605.22763v1) reports 9/353 formalized Erdős problems and 44/492 selected OEIS conjectures, with Lean proofs and selected natural-language proofs released in the [results repository](https://github.com/google-deepmind/alphaproof-nexus-results); the paper appeared in *Science* (DOI [10.1126/science.aej2213](https://doi.org/10.1126/science.aej2213)). This is a peer-reviewed system evaluation with public proof artifacts, not a claim that all 53 entries are independent, famous, newly discovered theorems. Formalization amendments and literature-priority questions still matter. The search system itself is not the released artifact, and we did not build every proof.
- **Axiom — CFSG.** The [public Lean repository](https://github.com/AxiomMath/CFSG) now states a sorry-free CFSG formalization over Mathlib/TauCeti with only Lean's standard axioms and gives the precise formal statement. Its README says the whole build used open Lake changes/optimizations and was brought under 24 hours. We verified that the repo and source are public through GitHub's API, but did not build the 43-million-line project or independently confirm the natural-language correspondence, build resources, or discovery timeline. The kernel claim and the announced project-scale claims are distinct.
- **Meta — formalization at scale and semantic translation.** The [ATLAS paper](https://arxiv.org/html/2605.29955v1) describes 45,000 declarations across 26 textbooks and explicitly distinguishes kernel validity from fidelity of the formal statement. A separate KCL/Cambridge preprint, [“Navier–Stokes lost in translation”](https://arxiv.org/html/2610.08144v1), argues that particular AI autoformalizations, including a released OpenAI Navier–Stokes case, fail to preserve some natural-language claims. This is a technical preprint critique, not treated here as settled adjudication; its concrete statement/proof comparisons reinforce the need for semantic audit beyond successful compilation.
- **Other labs / search boundary.** The targeted search found DeepSeek's public theorem-proving benchmark work, but no independently verified new theorem claim from DeepSeek or xAI in the queried sources comparable to the above 2026 releases. This was a bounded web/repository search, not proof that no such result exists.

## Verdict

FOTAR is a genuinely new implementation in this repository, but the underlying dictionary mechanism has clear prior art. It is exact on tested cases and its table now has an in-band reader. It has **not** produced a full-message Pareto gain, and its real OpenStack candidate loses by 195 tokens on the final run (184 on the earlier run). Retain it only as a guarded exploratory codec until a real prose/ops full-frontier win and a serialized-message-only parent reader are demonstrated; the current evidence does not justify claiming practical benefit.
