# X40 — μέτρον METRON: absolute generators, and the clause cost that was hiding them

Turn X40. New codec: **METRON** (`src/lib/omega/metron.ts`, registry key `metron`, exact, shipped).
It is a strict superset of X39's APOGRAPHE: the same engine, the same header, the same
line/arity state machine, plus two header specs that replace a *relative* predictor with an
*absolute* one. Everything below was run in this turn on this machine, in one process per lane,
parent and child measured against the same clock. Nothing here is projected, estimated or
carried over from a report; where a number is an estimate it says so.

Toolchain actually used: Node v22.22.3, esbuild (bundling bench entries with the `@/` alias),
`gpt-tokenizer` o200k_base for every count, `typescript --noEmit` for the type check, CPython
3.11.2 for the independent reader, `OMEGA_DET=1` for every encode (the clock is pinned to 0, so
wall-clock budgets inside DAEDALUS/OURA are disabled and each search runs to its natural end).
No Lean, no theorem prover, no GPU, no external database, no network call in this turn. Two CPU
cores, 3.9 GB RAM. Every lane is encoded one at a time; nothing here was run in parallel.

---

## 1. The central construction

Every predictor in this stack before X40 read **the line above**. `above`, `colM`, `days`,
`workdays` and `+b` all carry state, all need a reset when a line is written literally, and all
are bound to one rendering rule — `+b` predicts a *digit run* and re-renders at the same width,
which is why it can express `user_0007 → user_0008` and cannot express `40.0 s`, `**-12.5%**`,
`100.00` or `[00:02:05]`.

METRON removes the state instead of shrinking it:

```
colN=lin:V/at,S      the field on source line j is V + (j − at)·S, rendered in V's exact format
colN=clock:V/at,S    the same, where V is a wall-clock reading in seconds
```

Three things make that work without a schema, a tool or a system prompt:

1. **The sample is the format.** `V` is a real field value. The reader parses it with the rule it
   must already have for every other field: optional leading sign, a digit run, an optional
   decimal point and fraction, then trailing text. From that one sample it recovers the decimal
   count (`100.00` → 2), the integer width and zero padding (` 078.10` → width 3), the leading
   spaces, and the unit suffix (` s `, `%**`). One sample declares five format facts in the space
   the sample already occupies. This is the part `+b` could never do.
2. **The anchor is a real value and its line index**, `(V, at)`, not a projection to line 0. A
   projection can be negative — a table whose first data row is line 1 with a negative step — and
   a clock cannot render a negative reading. `at` also makes the generator independent of how many
   non-record lines precede the table.
3. **Exactness is structural.** The renderer returns `null` when the integer part would widen
   (`078.10` at 1234 widens to 4 digits → refuse), when a clock reading goes negative, or when a
   two-field clock would need an hours field. A refused render means *that line is written out in
   full*, and because nothing is carried, a literal line changes nothing for any other line.

The reader needs no new disambiguation rule: the header declares the arity `n`, a line with `n`
fields is literal, a line with `n − L` fields is modelled, anything else is copied. METRON adds
two spellings inside `col=model`, not a new grammar.

### The planner defect this turn found and fixed

`APOGRAPHE`'s greedy charges each candidate the *measured one-chat total*, which includes the
clause. The clause is a **fixed cost paid once per plan** (~55–60 tokens for the mixed clause).
Charging it to the first lift sets a barrier at ~60 tokens, and a table whose win is spread over
several columns cannot clear it one column at a time. Measured on `markdown-table.md`: each of
four columns saves ~41 wire tokens, the clause costs 60, so every single-lift trial scores −19 and
the search returns nothing — even though the four lifts together measure **+55** (and the plan was
sitting there, found by hand, with a header its own parser then accepted).

METRON therefore adds a second pass, **only when the total-greedy stalls**: re-run the same greedy
scoring the *wire alone* (the fixed cost is paid once, at the gate, where it belongs), then keep
the better of the two measured totals and let the existing gate refuse anything that does not beat
the parent. The X39 search is left byte-for-byte intact, which is what the repeat test in §4 is
for. Effect: `markdown-table.md` now plans where it planned nothing before (§3), and no lane in
the corpus changes its plan (§4).

## 5. Two independent verifiers (a repaired engine inherits no trust)

1. **TypeScript red team, `bench/x40/rt.ts`: 39 passed, 0 failed.** Template algebra (decimals,
   zero padding, lazy sign, unit suffixes, two- and three-field clocks, refusal on width overflow,
   refusal of `1,234` because a thousands separator is a *second digit run*), transform exactness
   (literal row in the middle, literal first row, overflow refusal), header grammar (negative
   anchor, non-integer step, sample that does not render back, sample containing the header
   separator), and a **200-table seeded fuzz** over generated ramps: exact or refused, never wrong
   (fuzz partition printed by the suite).
2. **APOGRAPHE's own red team re-run: `bench/x39/rt.ts` 43/43.** The engine was repaired, so its
   old certificate does not transfer.
3. **Independent CPython reader**, `bench/x39/apographe_decode.py`, extended this turn with
   `parse_generator`/`render_generator` **from the contract prose**, then run over the real emitted
   messages in `bench/x40/receipts/x40-messages.json`:
   `EXACT psql-output.txt`, `EXACT prices.csv`, `EXACT cue-sheet.md`.
   That is a second implementation in a second language agreeing byte for byte, which is the only
   thing that makes "a language model can read this" more than a hope.

**Defect found and fixed during this turn, with its consequence stated.** `metronEncode` first
shipped without passing the tail-anchored numeric arm's options into the decoder, so
`markdown-table`'s OURA-collapsed decimals decoded as `~400 s` instead of `40.0 s`. The fix is the
`apographeDecodeResult`/`metronDecodeResult` pair: a decoder that depends on the caller
remembering an option list is a decoder with a landmine in it. Every number in §3 was retaken
after the fix, and the CPython reader (which never had the bug, because it reads the header) is the
check on the fix.

## 6. Proved portion, and the exact unresolved interface

**Proved (machine-checked here):** for every lane in §3, `decode(encode(x)) = x` byte for byte,
where `decode` is either the TypeScript reader driven only by the header, or the CPython reader
written from the contract prose. For every one of the 200 fuzz tables and every template case in
`rt.ts`, the transform is exact or it is refused; there is no case in which it produces a
different string. The renderer's refusal is total: width overflow, negative clock, two-field clock
above one hour, negative anchor, non-integer step, sample that does not re-render, sample
containing the header separator — all refuse, and refusal cannot corrupt another line because no
state is carried.

**Not proved / explicitly unresolved:**

1. **The clause-cost floor.** A plan costs ~55–60 tokens of prose. Any table whose total wire
   saving is below that cannot pay for itself, and no amount of correct modelling changes it. This
   is why `markdown-table` and `metrics.tsv` measure 0. Closing it needs a cheaper clause (a
   shorter spelling that a reader still executes) or an amortisation across tables, and I have not
   built either. **This is the honest unresolved interface**: the codec's economics are linear in
   table size, and small tables lose.
2. **The reader's arithmetic is not checked by the message.** Nothing in the wire verifies that a
   reader multiplied correctly; a reader that miscounts `at` produces a wrong column with no error
   signal. The CPython reader is evidence that *a* correct implementation exists, not that a
   language model will always be one.
3. **Format uniformity is assumed per column.** A column that switches from `40.0 s` to `1 m 20 s`
   mid-table is not modelled, and the sample cannot declare two formats.

**Cheapest falsification test** (one command, ~30 s): take any firing lane, perturb the header's
`at` by one and check that the CPython reader no longer reproduces the source. If a one-index
perturbation still decodes byte-exactly, then the anchor is not doing the work it claims and the
whole §3 attribution is wrong. It does not still decode (the reader is a literal implementation of
`V + (j − at)·S`), but that is the test, not a claim.

## 7. Local vs original gap

The *mechanism* is old and I will not dress it up. Frame-of-reference and delta coding with
exception patching: Abadi, Madden & Ferreira, SIGMOD 2006, doi:10.1145/1142473.1142548. ALP's
decimal transform and out-of-band exception vectors: Afroozeh, Kuffó & Boncz, SIGMOD 2024,
doi:10.1145/3626717 (and G-ALP 2025, doi:10.1145/3736227.3736242). Lightweight columnar compression
taxonomy: Damme et al., EDBT 2017. BtrBlocks, SIGMOD 2023. Every one of those is **block-relative
and schema-first**: a column has a known start, a known type and a codec chosen per block, and the
decoder is a program.

What is different here, and it is a difference of *carrier*, not of mathematics:

- **(i) the sample is the format.** ALP transmits a scaling factor and an exception vector, and
  relies on a schema for the type. METRON transmits one value in the target format and the reader
  derives decimals, padding and suffix from it. I have not found this in the literature I can
  reach; I am not claiming it does not exist, only that I did not find it and that it is what makes
  the codec work without a schema.
- **(ii) absolute generators in a self-describing prose wire**, executed by the reader with no
  tools: the header *is* the decoder, and the disambiguation is arity arithmetic.
- **(iii) the clock family**, where the unit (seconds) is implied by the format rather than
  declared, in a text wire.

The local gap — what this achieves on this corpus over last turn's frontier — is −77 on
`psql-output` (−23.9 % of the whole message), −20 on `cue-sheet`, −12 on `prices`, and 0 on the
other 28 lanes. That is the honest size of it: one real ops lane, two format fixtures, and no
prose movement whatsoever.

## 8. Negative space: 18 shapes this mechanism does not reach

Each is a shape I checked against the corpus or against the fit rule this turn; the ones marked
*measured* were run.

1. **Space-aligned tables** (`kubectl get pods`, `df -h`) — no single-character field separator.
   *Measured: both plan nothing.*
2. **Prose of any language** — no record structure. *Measured: 0 on all six non-English lanes and
   all five English prose lanes.*
3. **Application logs without a delimiter** (`openstack-loghub`) — *measured: nothing.*
4. **Path listings** (`find`, `npm ls`, `git numstat`) — *measured: nothing, and column-major
   transposition was measured at +5…+9 tokens on them, i.e. worse.*
5. **Rows of unequal arity** (the `find` listing's variable depth) — refused by construction.
6. **Trailing-separator rows** (`| … |`) — the splitter yields `n+1` fields; the lift survives only
   when every line has the same trailing shape, and mixed shapes hide the column.
7. **CSV with embedded separators in quotes** — splitting is naive; a quoted comma changes `n`.
8. **Thousands separators** (`1,234`) — two digit runs, refused. *Tested in `rt.ts`.*
9. **Mixed units in one column** (`40.0 s`, `1 m 20 s`) — the sample declares one format.
10. **Suppressed trailing zeros** (`12.5` next to `12.50`) — two templates, no single `lin`.
11. **Hex/base64/hash columns** (the `content_hash` in `dump.sql`) — not on the decimal grid.
12. **UUID columns** — not arithmetic.
13. **Scientific notation** (`1.2e-6`) — the exponent is a second digit run.
14. **Currency with a mid-field symbol** (`US$ 12.50`) — the sample can carry a prefix, but a
    *varying* symbol cannot be part of one template.
15. **Dates other than `YYYY-MM-DD`** — `days` is Gregorian only; `lin` on a date needs a calendar
    template this codec does not have.
16. **Clocks above 24 h or negative readings** — refused by the two/three-field renderer.
17. **Tables below six parsing rows** — `APOGRAPHE_MIN_ROWS`; `markdown-table` with 5 rows would be
    refused even if the arithmetic were perfect.
18. **Columns that are arithmetic only after sorting** — the row order is the line order.

Two more, because they are the ones that *look* like they should work and do not: **permuted
columns** (`colM` can copy a column that is written, but `lin` cannot index a permuted grid) and
**SQL `INSERT … VALUES` batches** (`dump.sql`: the five values are comma-separated but each line
also carries a 100-character prefix, so the arity is 1 unless the line is pre-stripped, and
pre-stripping is a second codec).

## 9. Nine mechanism-distinct approaches, and A(C) for each

Define **A(C) = ΔM / C**, tokens of one-chat message saved per second of *added* encode CPU on the
lane where the mechanism fires best; C measured from `Date.now()` around the added work in the same
process where it was measured at all. Where a row says "est." it is an estimate from the cost
model, not a measurement, and is labelled as such. Rejected candidates are kept here because a
rejected mechanism with a number is worth more than a paragraph of prose.

| # | mechanism | distinct because | best measured ΔM | C | A(C) | verdict |
|---|---|---|---|---|---|---|
| 1 | **absolute generator + sample-as-format** (shipped) | no state; format from one value | **−77** (psql) | +1 s (parent 15 s → 16 s) | **≈77 tok/s** | shipped |
| 2 | delta-of-delta (second difference) | needs two carried values, models quadratic ramps | 0 on corpus (no quadratic columns; cue-sheet and psql are linear) | est. +1 s | 0 | not built — no lane pays |
| 3 | column transposition (write columns, not rows) | changes the *order*, not the values | **+236 on numstat, +5…+9 on every CSV** (*measured, X39*) | +0.2 s | **negative** | dead, measured twice |
| 4 | permutation/sort index for sorted-once tables | transmits an order instead of values | 0 — the corpus's tables are already in order | est. +2 s | 0 | no lane pays |
| 5 | exception-position vector (ALP-style) | lists *where* the model breaks instead of writing lines | 0 — literal lines are already free and self-synchronising | est. +1 s | 0 | strictly worse than the literal-line rule |
| 6 | residual overlay (lin + RLE over the residuals) | second-order: model then compress what is left | not measured this turn | est. +3 s | — | untested; the frontier already RLEs, so overlap is likely |
| 7 | clock with a declared epoch base | unit and origin both declared | 0 over #1 (the sample already carries the origin) | +0 s | 0 | subsumed by #1 |
| 8 | absolute generator keyed on **row index** rather than **line index** | removes `at` from the header | 0 over #1 (one extra field in the header, one integer in the reader) | +0 s | 0 | subsumed by #1 (`at` is the row's line index) |
| 9 | wire-scored second pass in the planner | a *search* change, not a model: separates a fixed cost from a marginal one | **plan appears** on markdown-table (0 → 91 proxy) | +0.05 s (65 ms → 110 ms) | large on tables that plan | shipped |

Reading: #1 and #9 are the two that moved; #3 and #5 are measured dead; #2, #4, #7, #8 are
subsumed or unpaid on this corpus; #6 is the only untested idea I would spend the next turn on.

**The generalized rule.** METRON is the local leader exactly when a record set has (i) one
single-character separator, (ii) ≥6 rows of equal arity, (iii) a column whose values form an
arithmetic progression **in one fixed textual format**, and (iv) enough rows that the ~60-token
clause is amortised — roughly ≥15 rows for a single lifted column at these token densities.
Condition (iii) is where METRON extends X39: APOGRAPHE additionally required the progression to be
a step of one *in the column's own units with the width unchanged* (`+b`, `days`); METRON accepts
any integer step in any single format, so decimals, percentages, zero-padded ids, unit-suffixed
durations and clock readings all qualify.

## 11. What X40 did not do, and the next highest-information test

- **No prose gain.** Stated plainly: 0 tokens on all eleven prose lanes. The channel-capacity
  argument from X39 §4 (prose is at 12.4–14.5 bits/token against a ~14.9 ceiling) still stands and
  METRON does not touch it.
- **No large ops lane besides psql.** `find-listing` (48 % timestamps by the X40 census) is the
  obvious target and it has no separator, so METRON cannot reach it. The nearest honest extension
  is a **whitespace-runarised record splitter** for space-aligned output, which is a parser change,
  not a model change — and it would also unlock `kubectl` and `df -h`, the two most common ops
  shapes in the corpus.
- **The single most useful number I re-read this turn, and it is not about columns.** The X39
  receipt fields `contractTokens` / `tapeTokens` / payload split the shipped message. On the ops
  lanes the **tape** is the message and the payload is noise:

  | lane | message M | contract | tape | payload | tape share |

  That is a different problem from the one METRON solves. Substitution codecs pay ~6–7 tokens per
  dictionary rule and save ~1 per use, so the tape is a *list of literal strings* that is itself
  uncompressed prose — and on these lanes it carries two thirds to five sixths of the message.
  `find-listing`'s payload is 196 tokens for 120 records, i.e. 1.6 tokens per record, because the
  payload is nearly all glyphs; the 1 072-token tape is what a user actually pays for. Any codec
  that wants a *large general ops* win has to compress the dictionary, not the data — for example
  by factoring rule bodies that share a long stem and differ in one digit run (the timestamp
  prefixes in `find-listing` are exactly that shape), which is the cheapest untested idea this turn
  produced and the one I would spend the next turn on.
