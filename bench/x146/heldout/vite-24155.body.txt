"Fixes #24142\n\nA transform request that starts while `hotUpdate` hooks run gets cached after the update with pre-update import URLs, so a self-importing module (like every Fast Refresh module) loads twice.\n\nRoot cause, traced through the dev server code:\n\n- `handleHotUpdate` takes its timestamp at the top (hmr.ts), before the `hotUpdate` hooks run, and passes that same timestamp to `updateModules` afterwards.\n- `invalidateModule` with `isHmr` only set `lastHMRTimestamp` and never touched `lastInvalidationTimestamp`, so the guard in `transformRequest` (`timestamp > lastInvalidationTimestamp`) had nothing to compare against. Any request started during the hooks passed it.\n- So the in-flight result was cached, and the module served at the new `?t=` imported itself at the old URL.\n\nThis PR does two small things:\n\n- `handleHotUpdate` takes a fresh timestamp when it calls `updateModules`, after the hooks have run.\n- HMR invalidation now also records `lastInvalidationTimestamp`, so the existing guard in `transformRequest` rejects results from transforms that started before the invalidation.\n\nAdded a regression test in `hmr.spec.ts` that starts a transform during a slow `hotUpdate` hook and checks the result is discarded, not cached. It fails on main (the stale result gets cached with the old `?t=`) and passes with this fix. The other specs in `hmr.spec.ts`, `moduleGraph.spec.ts`, `transformRequest.spec.ts` and `moduleUrl.spec.ts` all pass.\n\nI used an AI assistant while tracing this, then went through the code paths myself before writing the fix: the timestamp flow in `handleHotUpdate` / `updateModules` / `invalidateModule` and both `transformRequest` guards. The fix and the test are my own calls.\n"
