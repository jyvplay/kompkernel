# X33 — OIKONOMIA: the allocation

**Codec:** `src/lib/omega/oikonomia.ts`, registry key `oikonomia`, family `exact`, fidelity `exact`.
**One-line result:** encode is **1.99× faster** across 38 lanes (median 2.19×, max 3.22×) for
**+15 tokens out of 23,610 (+0.064%)**, with **38/38 byte-exact** and two disclosed regressions.

---

## A. The problem, restated honestly

X32 closed with a defect it named itself: encode takes 7–135 s, and below ~1200 characters it
returns the input unchanged after all of that work. X30 had already made encode time an in-scope
metric. X33 was told to attack it, and to do so with a *new codec*, not a tuning pass.

The stack is also, as the user put it, **benchmaxxed**: 21–52 % retention on ops and tabular text,
74–96 % on prose, and nothing at all on short prose. X32's own external finding (arXiv 2607.23362,
JOLT) explains why that ceiling is near-immovable *within the mechanism family*: BPE already sits
within 1–2 % of the LP lower bound, so choosing a better character string has almost no headroom
left. That is an argument for spending this turn on the axis the family has never optimised —
**the cost of finding the string** — rather than on the string.

So X33 does not claim a compression gain. It claims a **cost gain**, and it measures the token
cost of that gain and reports it.

## C. Finding 1 — the long-string token-count memo (94.9 % redundant)

X30 measured 2 240 610 `countTokens` calls on one encode, found 98 806 distinct strings, and
memoised **strings under 24 characters** (`SHORT_CACHE`). The other side of that split was never
measured. It is three orders of magnitude smaller by call count, so a call-count profile cannot
see it — but it dominates by *work*:

Instrumented on `prose-01` (`bench/x33/ct.ts`, configs = 1):

```
short calls (< 24 chars)     2,384,798     distinct ~98,000
long  calls (>= 24 chars)       65,364     distinct   3,312     94.9% redundant
mean length of a long call      1,738 characters
chars pushed through the pretokenise regex   113,629,256
```

**113 million characters through a regex, on a 3 370-character input, 94.9 % of it repeated.**

Fix (`src/lib/omega/bpe.ts`): memoise the long path too, keyed on the whole string. The memo is
**exact** — same string, same encoding, same count — so it can change timing and never a number.

The key is the string itself, **not** `enc + '\u0000' + text`: building that concatenation
allocates another ~1.7 KB on every call, which is precisely the cost being removed. The short
cache had the same flaw at 2.4 M allocations per encode, so both caches are now **one Map per
encoding**.

Measured effect, in isolation, on four lanes (identical tokens, all byte-exact):

| lane | before | after long memo | after both |
|---|---|---|---|
| kb-article | 19,503 ms | 15,716 ms | 15,279 ms |
| de-kb | 19,402 ms | 18,554 ms | 19,745 ms |
| node-stacktraces | 26,973 ms | 22,956 ms | 21,381 ms |
| prose-01 | 32,536 ms | 22,226 ms | 20,839 ms |

1.05–1.56×, and the widest gain is on the lane that was slowest.

## D. Finding 2 — the propagation gap, and three nulls that measured nothing

`syntomosEncode` called `metathesisEncode(text, enc)` with **no options object**.
`metathesisEncode` called `symplokeEncode(text, enc)` with none. So `budgetMs`, `maxEvals`,
`restarts`, `wordGrid` and `capGrid` — passed by callers of every codec above SYMPLOKE since
X28 — were delivered into a void.

That is not tidy-up. It invalidates three published results:

| turn | claim | status |
|---|---|---|
| X28 | "the search budget is not binding" | measured with a disconnected knob |
| X31 | "widening the budget does not help" | same |
| X32 | "the wordGrid / capGrid grid is saturated" | same |

(HEURESIS's `scriptTries` was the one knob that ever worked, and only because it is delivered by
environment variable rather than by options.)

X33 forwards the options through `syntomos → metathesis → symploke`, then re-asks two of the three
questions with a knob that reaches the code:

* **sibyl budget** 300 ms vs 1200 ms vs 6000 ms vs default — *identical tokens* on kb-article,
  de-kb, node-stacktraces, prose-01. **The X28/X31 conclusion survives, now for a real reason:**
  the searches finish before their budgets expire. It is a sound null rather than a vacuous one.
* **polytropos config count** 6 vs 3 vs 2 vs 1 — identical tokens at 6, and **3 or fewer loses**
  (de-kb 457→458, node-stacktraces 300→304). **The X32 grid conclusion is refined, not confirmed:**
  the budget is slack but the *config count* is load-bearing, and the config count was never the
  thing under test.

## E. Finding 3 — 83 % of the encode is one parent run four times

Timing each SYMPLOKE parent (`OMEGA_PARENT_TIMING=1`, `bench/x33/par.ts`), prose-01:

```
  parent lakonikos      2109 ms
  parent daedalus        580 ms
  parent polytropos     4980 ms
  parent polytropos     4283 ms
  parent polytropos     4514 ms
  parent polytropos     4727 ms
WINNER parent msg 737 TOTAL ms 22296
```

**Four polytropos runs: 18.5 s of 22.3 s, 83 % of the encode**, where a reader of the code would
expect one.

The cause is SYMPLOKE's `'in'` shape order. Shapes (digit runs, timestamps, mechanically
expandable forms) are collapsed either **out** — after the grammar runs, on the wire, free — or
**in** — before the grammar runs, on the source. The `'in'` order owes a **full parent re-run to
every trial**, because each trial hands the parent a genuinely different input (the source
collapsed with that trial's shape set). They cannot be cached; they are distinct work.

X24 set the trial cap to 4. Nothing had ever measured whether 4 was worth more than 1.

It is, sometimes. Across 33 lanes, capping at 1 trial:

```
total encode time   1,645,695 ms  ->   787,429 ms      2.09x faster
total message tokens    24,726    ->    24,778         +52  (+0.21%)
byte-exact                                             33/33
```

And the decisive structural fact: **the five lanes that lose are exactly the five lanes on which
the `'in'` order wins.** No lane loses for any other reason. The correlation is perfect in both
directions, which tells you the entire question is "should I buy `'in'` trials at all?"

## F. The mechanism — buy the next trial only when the last one paid

**Prediction was tried first and failed.** The obvious signal is how much the shape set collapses.
Measured over 44 lanes (`bench/x33/pred.ts`), total collapse count does not separate the classes:

| lane | source collapses | verdict |
|---|---|---|
| find-listing.txt | 240 | `'in'` wins |
| aapl-2014.csv | 240 | `'in'` loses |
| vix-daily-1990.csv | 126 | `'in'` wins |
| ls-full-iso.txt | 56 | `'in'` loses |
| npm-ls.txt | 0 | `'in'` wins |

Size, category and shape count were tried too; none separate.

So OIKONOMIA does not predict. It **buys information one step at a time** and purchases the next
step only if the previous one paid:

```
trial k improves on the incumbent  ->  buy trial k+1
trial k does not improve           ->  stop
```

This is the right shape for this search rather than a bolted-on heuristic, because the trials are
greedy and ranked by hit frequency: a trial that fails is the **most frequent remaining
candidate** failing, which is the strongest available evidence that the rest will not pay either.

Measured on the eight lanes where the question arises at all, **one trial already reaches the
four-trial answer on six of them** (`bench/x33/caps.sh`):

| lane | cap 2 | cap 4 | order 2 / 4 |
|---|---|---|---|
| vix-daily-1990.csv | 1195 | 1195 | in / in |
| kubectl-get-pods.txt | 340 | 340 | in / in |
| npm-ls.txt | 901 | 901 | in / in |
| psql-output.txt | 322 | 322 | in / in |
| openstack-loghub-26.log | 945 | 945 | in / in |
| meeting-transcript.txt | 385 | 383 | out / in (**+2**) |
| find-listing.txt | 1279 | 1266 | out / in (**+13**) |
| dump.sql | 686 | 662 | in / in (**+24 at cap 2**) |

The gate is conservative on exactly the lane that needs it: **dump.sql's first trial *does*
improve (707→686), so the gate keeps buying and reaches 662** — the gate recovers dump.sql
entirely, which a flat cap of 2 does not.

## H. Decodability

Unchanged, and it needs no new argument. OIKONOMIA emits wires produced by the same code paths as
TIMEMA's: same glossary, same tape, same contract, same `chironDecode`/`symplokeDecode` reader.
The only thing that differs is **how many times the encoder is willing to re-run its own search.**
Any wire OIKONOMIA emits is a wire TIMEMA could have emitted.

X32's live hand-decode receipt (a 13-rule wire from a 192-token ops log, read back to the byte by
a bare model from the message text alone, no system prompt, no skills.md, no tools) therefore
carries forward unchanged. It remains **n = 1 reader, 1 message** — a proof of existence, not a
reliability rate.

Verification this turn: `bench/x33/verify.ts`, 5 lanes, `oikonomiaRoundTrip` → **all true**.

## I. Negative space — what was measured and rejected

1. **Predicting `'in'` from the document.** Collapse count, size, category, shape count, all tried
   on 44 lanes; none separate the classes (§F). Rejected — replaced by incremental buying.
2. **Flat trial cap.** cap = 1 is 2.09× faster but loses 52 tokens across 33 lanes, including
   +24 on dump.sql. Rejected in favour of the gate, which recovers dump.sql entirely.
3. **Cutting the polytropos config count.** 3, 2, 1 all lose tokens (de-kb 457→458,
   node-stacktraces 300→304). Rejected; configs stay at 6.
4. **Lowering the sibyl budget.** 300 ms to 60 000 ms: identical tokens. The budget is slack, so
   there is nothing to reclaim. (Also re-confirms X28/X31, this time validly.)
5. **Lowering the polytropos budget.** 25 000 → 8000 is token-neutral and ~13 % faster, but the
   gain is subsumed by the cap gate and adding both knobs buys complexity, not seconds. Not
   shipped; the env hook (`OMEGA_POLYTROPOS_BUDGET_MS`) is left in place with a comment.
6. **Caching the `'in'` parent runs.** Impossible as stated: each trial runs the parent on a
   different collapsed input. This is why the trials are expensive rather than merely wasteful —
   the obvious fix does not exist.
7. **Grammar transfer** (build the dictionary once, apply it to each collapsed variant). The
   attractive version of §6 and the one that would make `'in'` trials nearly free. Not
   implemented: it requires reaching into sibyl's search internals, and the rules found on
   `text` are not sound for `collapse(text, shapes)`. Left as the clearest next lever.

## J. Honest external context (new sources this turn)

* **arXiv 2604.02985, "Prompt Compression in the Wild"** (Apr 2026, >30 000 end-to-end runs).
  The most directly relevant external result found in any turn. It reports that **"for short
  inputs (≤1 000 tokens), compression caused overhead, reducing speed-ups to 0.9–1.0×"** and that
  **"in all other settings — especially with vLLM or commercial APIs — the compression overhead
  outweighs any benefits."** It also finds *"model inference accounts for only about 5 % of total
  latency"* in LLMLingua, i.e. the compressor's own algorithm dominates. This is independent,
  published confirmation that overhead, not compression ratio, is the binding constraint on this
  whole family — which is the premise of X33.
* **arXiv 2609.32961, "Beyond Token Savings"** (Sep 2026, ~35 000 agent runs). **"Fewer tokens
  need not mean faster or cheaper execution"**: on Terminal-Bench, policies using roughly a third
  as many tokens take 20–80 % longer. A needed corrective to reading any token count as a win.
* **arXiv 2603.23525** (pre-registered trial). Gives the break-even algebra: at compression ratio
  0.5 their corpus tolerates at most a **1.17 % output expansion** before all input savings are
  erased.
* **arXiv 2602.13266, "LoPace"** (Feb 2026). Lossless prompt *storage*: 4.89× mean ratio at
  3.3–10.7 MB/s over 386 prompts. Different constraint set (the output is not model-readable), but
  it sets the throughput scale: **3.3 MB/s**. Our encoder runs at roughly **0.0002–0.0005 MB/s**.
  That gap is the honest measure of how much further this axis has to go, and it is not closed by
  a 2× win.
* **arXiv 2506.00307, "Lossless Token Sequence Compression via Meta-Tokens"** (Jun 2025). The
  closest published relative: a repeated subsequence of length *L* occurring *n* times costs *L·n*
  tokens versus *L + n* with a dictionary entry — **our mechanism, stated explicitly.** It reports
  ~100 ms pre-processing latency but requires **fine-tuning the model** to read the format. Our
  differentiator is precisely that we do not.
* Practitioner corroboration of the short-message cliff: **"Very short contexts (under roughly
  500 tokens), where compression overhead exceeds savings"** (compresr.ai, Sep 2026) and **"What
  NOT to cache: … short prompts (overhead not worth it)"** (amirteymoori.com, Aug 2026). Two
  independent sources stating the threshold X32 measured empirically.

## K. openai/math — re-audit

> No Lean toolchain and no theorem prover is installed in this sandbox; no proof was
> machine-checked here. What follows is a read of what others published and verified.

**The repo changed since the last audit.** As of 2026-10-20 the OpenAI mathematics repository
shows `pushed_at` 2026-10-12, 0 open issues, 0 open pull requests — but the scale of the release
is far larger than in earlier turns: **722 manuscripts, 372 "result families", 17 areas**, posted
2026-10-06.

**What is claimed.** UGC; a zero-free half-plane for the Riemann zeta function; the rational Hodge
conjecture for CM abelian varieties; isomorphism of the free group factors. Earlier in 2026:
the **Erdős unit-distance conjecture (1946) disproved** (20 May 2026), verified in a companion
paper by nine mathematicians including Gowers, Alon, Wood and Bloom, with Sawin refining the
bound to δ ≥ 0.014; and on 1 Aug 2026, **ten results** from the internal Astra model — non-sofic
group (open since Gromov 1999), Connes rigidity disproved, Ehrhart's volume conjecture, Erdős
183/146/180 — with Lean 4 certificates, `"sorry"` count zero, Apache 2.0, reportedly ~$2 000 of
compute.

**How much is actually checked — the number that matters.** 235 of 372 families carry a Lean
scope document; the formalisation catalogue lists 162 individual manuscripts whose main result is
formalised. So **137 families have no formalisation at all**, and OpenAI's own README warns that
*"some of the unformalized results could have issues."* The library is ~122 000 Lean files,
~26 M lines, built on ~30 outside formalisation projects, some patched for compatibility.

**The UGC / faithfulness thread, deeper.** Two independent audits now exist and neither answers
the question that decides the result. `lgboim/unique-games-short-proof` ran the Comparator check
on 9 Oct 2026 at rev `fd4aeeb` under Lean 4.34.1: kernel accepted, axioms `propext`,
`Classical.choice`, `Quot.sound` — but the sandbox was not enforced and, by their own statement,
they did **not** audit whether the formal statement matches the papers' main theorem. Separately,
arXiv 2610.17090 surveys exactly this "statement faithful?" gap. A kernel accepts a *term*; it
does not certify that the *proposition* is the one the literature means. Until a human matches
`OAI.UniqueGamesTheorem.theorem11` against the UGC as stated, the correct grade is
**"formalised, not yet faithful-checked."**

**Process caveats that belong in any verdict.** None of the 722 has been peer-reviewed. Aaronson
(7 Oct 2026) reported no human appeared to have understood almost any of the proofs;
Moshkovitz called one "so horribly written that it's impossible to read it without AI help";
technology.org (14 Oct 2026) puts **58 % of top-line results at no machine check at all**. On the
unit-distance disproof specifically, the model reportedly succeeded on ~50 % of repeated runs, and
OpenAI published neither failure rates nor compute time. Separately, OpenAI **withdrew three
Hodge/Weil papers** after a sign error; none had been formalised.

## L. Limits of this turn

* **Single measurements, not distributions.** The pipeline is *not* deterministic — `Date.now()`
  is read inside control flow in `polytropos.ts`, `akribeia.ts`, `aion.ts`, `abacus.ts` and
  `amphora.ts`, and `OMEGA_DET=1` stubs only `clock.now()`. Every number above is one run. This is
  visible in the data: `npm-ls.txt` measured 901 in one run and 940 in another.
* **Part of the `'in'` benefit is best-of-*k* sampling, not a shape effect.** Some `'in'` winners
  (npm-ls, kubectl-get-pods) win with **zero** recorded collapses — they are drawing a second
  sample from a stochastic search. That is a real effect and it is part of what the gate
  preserves, but it means the honest description of `'in'` is "an order *and* an extra sample".
* **5 of 44 lanes crashed** in the sweep (including `package-lock-head.json`); results are for the
  38 that completed.
* **This is a speed codec, not a compression codec.** +15 tokens is a cost, not a gain.
