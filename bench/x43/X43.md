# X43 — KRISIS (κρίσις, "a judging, a decision")

Registry index **33**, `src/lib/omega/krisis.ts`, parent **APOCOPE** (X42, index 32).

Every codec shipped in this repository so far has tried to make the **wire**
smaller. KRISIS tries to make the **decision** cheaper. It exists because a
profile said the decision is where all the time goes.

**Result: identical token count on every lane tested, byte-exact, at up to 2.5×
lower wall clock.** KRISIS adds no clause, no marker and no alphabet — it changes
no wire at all. Its contribution is on the **time** axis, which this repository
made first-class in X30 and X41 and has never before optimized.

---

## 1. The measurement that produced it

`bench/x43/screen3.ts` timed each layer on `pom.xml`, a **1,797-character** file:

| layer | time | msg |
|---|---|---|
| chiron | 203 ms | 305 |
| anadiplosis | 9,865 ms | **242** |
| euteleia | 6,659 ms | 242 |
| oura | 33,424 ms | 242 |
| antistrophe | 94,988 ms | 242 |
| peritrope | 100,517 ms | 242 |
| systole | 140,598 ms | 242 |
| apocope | 138,127 ms | 242 |

**Six layers spend 138 seconds and every one returns 242 — the value ANADIPLOSIS
reached in 9.8 s.** On this lane the upper stack buys nothing and costs 93 % of
the wall clock.

The same shape at real sizes: **814 s** for a 6.5 KB CSV, **609 s** for an `ls`
listing, **2,393 s** for a log file — and, for the standing priority on everyday
prose, **328 s for prose-03** and **261 s for prose-05** against **8.8 s** for
prose-01. A user waiting thirteen minutes to compress a spreadsheet is not a
usable system.

### Where the time goes

Each layer computes its parent on the **unmodified** text and then runs a handful
of **trials** on transformed text, each trial a full recursive lower-stack
encode. Depth *d* with *t* trials per layer is **O(t^d)** lower-stack encodes.

The auctions are *not* the problem. `bench/x43/screen4.ts` on pom.xml:

```
ouraEncode(text) x1      :  36,505 ms   msg=242
auction (10 pairs)       :       2 ms   (0.2 ms/pair)  5 negative
one antistropheSwap      :       0 ms
one countTokens(swapped) :       0 ms
one TRIAL ouraEncode     :  12,036 ms   msg=242
```

**The auction costs 2 ms. One trial costs 12,036 ms.** The decisions are also
badly informed: ANTISTROPHE found **5 of 10** pairs with a negative raw delta, so
it ran two 36-second encodes — and both returned no gain, because the redundancy
a swap removes is redundancy ANADIPLOSIS had already removed.

OURA is worse. It ranks candidates by `est = spans.length * (k - 1)` — a count of
**characters** removed, not tokens — then runs up to **2 shapes × 3 modes = 6**
full lower-stack encodes on that heuristic (`oura.ts:398-405`).

### A cheaper layer was also checked, and it is not the bottleneck

`bench/x43/screen2.ts` ran CHIRON alone on the two prose/code lanes at four
budgets and two work-unit settings:

```
kb-article.txt   3,385 chars: budget default/4000/11000/26000 -> 656 every time
                 script=none rules=0 blocks=0, 66-185 ms
component.jsx    1,194 chars: budget default/4000/11000/26000 -> 296 every time
                 script=none rules=0 blocks=0, 29-98 ms
```

CHIRON emits the **raw fallback** with **zero rules** — and it is not out of time,
it finishes in tens of milliseconds. The smallest-grammar machinery finds no rule
on prose or code whose saving exceeds its own clause. So the grammar contributes
*nothing* on exactly the lanes the user cares most about, and the cost there is
in the layers above it.

## 2. The mechanism

KRISIS prices every layer's best candidate **once**, with a single tokenization
each, and compares it against the cost of the clause that layer would have to add:

> **skip layer L  iff  bestRawDelta(L) + clauseCost(L) ≥ 0**

This is the reasoning PERITROPE already uses to choose its **depth** — *"a pair
that saves three tokens raw may cost two to state"* — applied instead as an
**admissibility gate on the trial itself**. Nothing in the stack did that before.

Evidence per layer, all cheap and all using exported transforms:

| layer | candidate generator | benefit measure | clause |
|---|---|---|---|
| OURA | `ouraFind` | `spans × (k−1)`, optimistic | `KRISIS_OURA_CLAUSE = 8` |
| ANTISTROPHE | `antistrophePairsFor` + `antistropheSwap` | measured raw Δ | measured `antistropheClausesFor` |
| PERITROPE | `peritropeSearch` + `peritropeApply` | measured raw Δ + clause | measured `peritropeClauseFor` |
| SYSTOLE | `systoleChoose` | measured raw save | measured `systoleClauseFor` |
| APOCOPE | `apocopeChoose` | measured raw save | measured `apocopeClauseFor` |

### Why the gate is sound in the direction that matters

`bestRawDelta` is measured on the **source**, before the lower stack runs. X42
established that raw savings attenuate ~**20×** through this stack (aapl 915 raw
→ 43 shipped; vix 504 → 29), because the dictionary and shape rules already
capture most redundancy. So the raw delta is an **optimistic bound**: if the
optimistic bound cannot repay the clause, the realistic value certainly cannot.
**The gate can only skip a layer that was going to lose.**

It is deliberately *not* a lower bound on the final message. No cheap rigorous
lower bound exists: X42 proved `sum(ceil(W/3))` is tight for bare digit runs, but
the dictionary beats it by mapping digit strings to single glyphs, so no
character-level bound survives contact with the stack. KRISIS claims
**admissibility pruning, not optimality**.

### Adaptive allocation in both directions

The same measurement *spends more* where evidence is strongly positive:
ANTISTROPHE's trial count rises above its default of 2 when the best raw delta is
large relative to the clause (`KRISIS_DEEPEN_RATIO = 4`, capped at
`KRISIS_MAX_TRIALS = 4`). It fired on chart.svg (trials 2 → 3). Search effort
follows measured evidence both ways — which is what separates this from a timeout.

### What it costs the wire

**Nothing.** A gated lane emits exactly the wire the surviving layers would have
emitted anyway, so the contract is unchanged and the reader is handed the same
single-chat-box instruction as before.

### The stronger receipt: the wire is not merely equal in size, it is identical

A token-count match could in principle hide a different wire that happens to cost
the same. `bench/x43/wireq.ts` runs `krisisEncode` and the ungated `apocopeEncode`
in the same process and byte-compares:

```
component.jsx         krisis=  264 ungated=  264  WIRE IDENTICAL  len 886 vs 886
kb-article.txt        krisis=  622 ungated=  622  WIRE IDENTICAL  len 2777 vs 2777
meeting-transcript    krisis=  384 ungated=  384  WIRE IDENTICAL  len 1500 vs 1500
bibliography.txt      krisis=  667 ungated=  667  WIRE IDENTICAL  len 2158 vs 2158
```

Four of four **byte-identical**, not just equal in token count. This is the
receipt that matters for the single-chat-box requirement: KRISIS does not produce
a *different* message that happens to decode, it produces **the same message**, so
bare-LLM decodability is inherited from the parent unchanged and needs no new
argument. The gate's effect is confined entirely to which searches are run.

## 4. The honest limit — and the most interesting result of the turn

**The gate only fires where a mechanism is entirely ABSENT**, because source-raw
evidence does not discriminate winners from losers once the lower stack is in the
way:

| lane | antistrophe raw Δ | clause | gate | actual outcome |
|---|---|---|---|---|
| pom.xml | **−16** | 6 | KEEP | **no gain** |
| ls-full-iso | **−9** | 5 | KEEP | **is the winner** |

A **−16 that loses** and a **−9 that wins** cannot be separated by any test
computed on the source text alone. That is a real property of this stack, not a
defect in the gate — and it independently explains X42's central puzzle, why
APOCOPE priced 756 raw tokens on vix and delivered zero.

Consequences, stated plainly:

- Where the gate fires (prose and code, every candidate delta exactly zero) it
  removes whole layers: **2.5×, 2.0×, 1.6×, 1.5×, 1.3×**.
- Where cost sits in the **lower** stack (component.jsx, kb-article, prose-01) it
  changes nothing, because there was nothing to prune — those run in 7–9 s either
  way.
- Where the raw deltas look promising but the layers lose anyway (pom.xml), it
  cannot help. Fixing that needs a predictor computed *after* the lower stack,
  which is the expensive thing being avoided. That is the exact remaining gap.
- chart.svg at 0.8× is the cost of adaptive deepening (trials 2 → 3) on a lane
  where the extra trial did not pay. Bounded, and the only lane measured slower.

## 5. Two further measurements, both negative

**Glyph reassignment is dead — now by measurement, not by argument.** X42's
Floor 2 killed it on the grounds that an alphabet mapping must be stated
in-message. That argument was **wrong**: `chiron.ts:144` says the first letter of
the tape declares the script, so *nothing about the alphabet is transmitted*. The
mapping is free.

So `bench/x43/screen1.ts` measured it directly on the real aapl payload — 65 rule
letters, 697 occurrences, currently 463 tokens:

| target pool | usable | remapped | tokens | delta |
|---|---|---|---|---|
| (current Cyrillic/polyglot) | 65 | — | **1370** | — |
| latin-letters | 47 | 47/65 | 1413 | **−43** |
| latin+punct | 75 | 65/65 | 1390 | **−20** |
| latin+digits | 57 | 57/65 | 1387 | **−17** |

**Every alternative is worse.** The intrinsic pair-merge test that motivated it
(Latin 1.02–1.04 tok/pair vs Cyrillic 1.71, Greek 1.83, CJK 1.85, box-drawing
3.17, dingbats 3.86) was the **wrong measure**: rule glyphs sit next to *digits*,
not next to each other, and Latin-next-to-digit tokenizes worse than
Cyrillic-next-to-digit. The existing collision-ordered script choice is already
good. **Do not retry.**

Also confirmed: `chiron.ts:1344` picks the script **once**, by minimum collision
count, and the entire variant sweep (separators × blocks × macros) reuses it.
That is a real unexploited degree of freedom — it just has no value, because
every alphabet tried is worse than the one already chosen.

**Budget-limited search is not the bottleneck.** CHIRON's search stops on a wall
clock (`min(11_000, 800 + 1.1·len)`, sweep capped at 26 s) rather than on
convergence, which invited the hypothesis that it is merely out of time. Refuted:
on both prose lanes it returns the raw fallback with **zero rules in 29–185 ms**
at every budget from default to 26,000 ms and at 20,000 and 200,000 work units.
It is not out of time; there is nothing to find.

## 6. Greedy status, bounds, citations

**Greedy: YES, and that is the point.** KRISIS is a one-pass greedy admissibility
filter with **no backtracking**: each layer is priced once on the source text and
the decision is never revisited, which is exactly why it is cheap. It is **not
optimal** — a layer combination that only pays *jointly* would be missed, since
each layer is judged alone — and the residual risk is bounded only by the
optimism of the estimates, not by any proof.

**Time and CPU bound: yes, explicitly and by construction** — this codec's entire
subject *is* the time bound. The gate costs one tokenization per candidate plus
one PERITROPE beam search, measured **12–761 ms** across thirteen lanes; what it
removes is full recursive lower-stack encodes costing **tens of seconds each**.

### Newly cited, directly on this mechanism

- **arXiv 2607.27871 — *Search as Computation Allocation*.** Formalizes precisely
  this class: *"Many algorithms spend an internal resource before returning a
  decision and are evaluated only by the quality of that terminal output."* Names
  it a **terminal computation-allocation problem**, gives Bellman equations for
  optimal allocation under fixed budgets, priced computation and exact
  certification, and derives weighted A\* from maximizing expected incumbent
  improvement — recovering A\* at *w*=1 and GBFS as *w*→∞.
- **arXiv 2610.22858 — *Uncertainty-Aware Budget Allocation for Efficient LLM Tree
  Search*.** The closest published analogue of KRISIS's adaptive half: a
  **training-free** framework decoupling value from uncertainty, where *"values
  determine which candidates are promising, while uncertainty determines how many
  merit expansion, via uncertainty-aware pruning"*, reducing token usage and
  inference time while maintaining accuracy across beam search and MCTS.
- **Classical lineage — weighted-admissible search.** *Anytime-WA\**
  (arXiv 1110.2737) converts A\* into an anytime algorithm using an admissible *h*
  plus an incumbent upper bound to prune and detect convergence, bounding
  suboptimality by the weight *w*. **ARA\*** tunes its bound to available time,
  starting loose and tightening. **Rectangle Search** (arXiv 2312.12554) is an
  anytime beam search with the same bound and a completeness proof under an
  admissible heuristic. KRISIS is a deliberately crude instance: it has **no
  incumbent to tighten against**, because it never runs the search it is pruning,
  so it substitutes the only bound available — an optimistic raw-token estimate
  plus a measured clause cost — and accepts that the bound is loose.
- **arXiv 2601.11038** introduces the **Anytime Index**, quantifying
  quality-per-token across reasoning budgets rather than final accuracy alone —
  the right shape of metric for a codec whose contribution is time, not size.
- **arXiv 2609.00813 (AnySearch)** reports that a policy trained under *fixed*
  budgets fails to adapt when constraints vary at deployment — the failure mode a
  per-document gate avoids by measuring the document instead of assuming a budget.
  **arXiv 2602.09574 (BG-MCTS)** conditions search decisions on remaining budget.
- **The most striking confirmation of this axis is not from compression.** Google
  DeepMind report (arXiv 2602.10177, *Aletheia*) that the January 2026 advanced
  Gemini Deep Think reduced the compute for equivalent IMO-ProofBench performance
  by **approximately two orders of magnitude — ~100× — at equal graded quality**.
  The same pareto move KRISIS makes here, achieved there by training and here by
  pruning.

## 8. Runtime honesty

All measurement ran **sequentially in single node processes on a 2-core sandbox** —
no parallelism, no distributed search, no independent agents. Background sweeps
were run one at a time precisely because two concurrent benches would corrupt the
timing numbers this codec is about.

Tools actually used: `node` + `esbuild` + `gpt-tokenizer` (all measurement and all
encodes), `tsc --noEmit` (type gate), `python3` (repo edits), `web_search` (two
live searches this turn). **No Lean, no theorem prover, no model inference was
executed.** Every mathematical claim above is reported from search, not verified
by me.

The exhaustive digit enumeration cited from X42 (1,110,000 strings) was genuinely
exhaustive; nothing in X43 is sampled except the lane set, which is stated
explicitly in every table.

### The exact remaining gap, and the next highest-information test

**Gap:** the gate cannot separate a promising-looking layer that loses (pom.xml,
antistrophe −16 raw) from a modest-looking layer that wins (ls-full-iso,
antistrophe −9 raw), because both judgements are made on the source text before
the lower stack runs. A predictor computed *after* the lower stack would fix it,
but the lower stack is the expensive thing being avoided.

**Next highest-information test:** price the same auctions against
`chironEncode`'s output (203 ms on pom.xml, **178× cheaper** than the 36.5 s
`ouraEncode` trial it would replace) and measure how well post-chiron delta
separates the pom.xml losers from the ls-full-iso winners. If it separates them,
KRISIS's gate becomes predictive rather than merely conservative and the remaining
1.0× lanes move. If it does not, no cheap predictor exists and the trial tree is
irreducibly expensive — which would be worth knowing definitively.

## Supplement, added after the second pair of searches

### A published reconciliation of the glyph result

`bench/x43/screen1.ts` found that remapping the rule alphabet onto Latin makes the
aapl payload **worse** (−43 / −20 / −17 tokens), even though Latin pairs merge
intrinsically at 1.02–1.04 tokens/pair against Cyrillic's 1.71. Published
per-script densities look like they contradict that, and it is worth stating why
they do not.

**arXiv 2505.24689**, *Structured Encoding for Robust Multilingual Pretokenization*,
tabulates tokens-per-character under `o200k_base` on natural text: English (Latin)
**0.2152**, German **0.2128**, Vietnamese **0.2688**, Russian (Cyrillic)
**0.2314**, Arabic **0.2976**, Hebrew **0.4163**, Thai **0.3160**, Hindi
**0.3245**, Punjabi **0.4979**, Korean (Hangul) **0.5827**, Japanese **0.5268**,
Chinese (Han) **0.6260**. On that measure Latin *is* the densest script and
Hangul and Han the worst — the opposite ordering to what a rule alphabet wants.

The two results are consistent once the context is separated. Those densities are
measured on **natural text written in that script**, where within-script merging is
high because the tokenizer was trained on exactly those sequences. A rule alphabet
is the opposite case: an **arbitrary, information-dense sequence** of glyphs drawn
from one script and embedded in a **foreign context** — in aapl's payload, 697
glyph occurrences interleaved with digits and ASCII punctuation. There, adjacent
glyph-glyph pairs are rare, so what decides the cost is the glyph-to-digit and
glyph-to-punctuation boundary, and the existing Cyrillic/polyglot choice wins it.
**The published numbers do not transfer, and any future attempt at alphabet
reassignment should be priced in-situ, not from a per-script table.**

Related and newly cited: **arXiv 2602.11174**, *The Script Tax*, measures
tokenization-driven efficiency and latency disparities across scripts and reports
a substantial information-cost increase of **+19.7 %** for mBERT (8.06 → 9.65) and
**+47.1 %** for XLM-R (12.19 → 17.94) in bits per character, using BPC precisely
to avoid the "NLL paradox" from subword fragmentation. **arXiv 2610.01984**,
*Universal Byte-Level Encoding*, routes between UTF-8 and UTF-16 to reduce
cross-script token-budget disparities, and its tables make the same point from the
other side: at a 16K budget Greek costs **90.5** tokens against English **34.7**
and Cyrillic **75.4** — Greek is *worse* than Cyrillic on natural text, which
matches this repository's intrinsic pair test (Greek 1.83 vs Cyrillic 1.71) rather
than the naive expectation. **arXiv 2603.25309**, *Separate Before You Compress:
the WWHO Tokenization Architecture*, reports 61.7–77.2 % token reductions for
Sinhala and Hindi against o200k, Llama 4 Scout and DeepSeek V3 — evidence that
script choice is worth tens of percent when the corpus is one script, and therefore
that this repository's finding (no gain, because the payload is mixed and the
glyphs are already near their floor) is a statement about *this* payload and not
about scripts in general.

The **Erdős #728** resolution has its own writeup, **arXiv 2601.07421**, described

> On Jan 4, 2026, Barreto announced a proof from Aristotle, based on an informal
> argument from GPT-5.2 Pro. But the problem as stated on the website was **vague,
> with the intended interpretation from Erdős unclear**. Forum participants
> commented on this vagueness; **a consensus then emerged that this should be
> regarded as a partial result, which did not yet fully resolve the problem.** On
> Jan 5 Barreto again asked GPT-5.2 Pro whether its argument could be upgraded to
> tackle the version participants had now identified as *the* problem; it answered
> affirmatively, Aristotle was re-run, and it produced a formal proof on Jan 6.

So the *statement* of the problem, not the proof, was the hard part, and it was
resolved by a human community between two machine runs. The Lean kernel certified
the proof on both days; only the mathematicians could tell that the first one
answered a different question. That is exactly the gap Gemini's **arXiv
2601.22401** Appendix A raises about whether a formally verified proof addresses
the **intended mathematical meaning**, and exactly the Leiden Declaration's first
threat — plausible arguments difficult to distinguish from correct ones — with the
distinction here being about the *question* rather than the *answer*.

orchestrating the translation and lemma decomposition**.
