# X34 — PYKNOSIS (πύκνωσις, "condensation")

**Shipped:** `src/lib/omega/pyknosis.ts`, registry key `pyknosis`, family `exact`,
after `oikonomia`, before `chronos`.

**One-line claim:** every codec before this one compressed the same resource —
the fact that some span of the text occurs more than once. PYKNOSIS compresses a
different resource, the one thing left once the repetition is gone: **the
decoder's tokenizer charges different prices for different characters, and that
price list can be arbitraged.**

---

## A. Where X34 started: the residual is repetition-free

The X34 brief opened with arc 1, the exact-repeat family. It is **refuted** and
should not be revisited. The decisive measurement is the tape residual
(`bench/x34/resid.ts`):

| lane | raw repeat coverage | tape repeat coverage |
|---|---|---|
| openstack-loghub-26.log | 76.3 % | **0.0 %** |
| git-numstat.txt | 61.5 % | **0.4 %** |

Re-encoding the tape gains exactly nothing: 648→648, 509→509, 1511→1511.

Everything downstream of that is dead too:

* **Glossary entry ORDER** — `chironParseTape` is order-sensitive
  (`chiron.ts:281-299`); 300 random permutations give **0/300** valid.
  Dependency-respecting topological orders move the wire only ±2 tokens.
* **Glossary-of-glossary** — LZ redundancy of the glossary is 0–17 %
  (dump.sql 0 %, openstack 6 %).
* **Tape re-encoding** — 0 tokens on every lane tested.

Arc 1's one live artefact is the near-duplicate census (`bench/x34/near.ts`,
LCS ratio ≥ 0.75), parked in favour of arc 2:

| lane | near-dup lines | lane | near-dup lines |
|---|---|---|---|
| openstack | 18/27 | **kb-article** | **0/45** |
| dump.sql | 25/38 | **prose-01** | **0/51** |
| find-listing | 106/121 | vix | 123/128 |
| git-numstat | 271/401 | | |

Top LCS ratios run 0.90–0.99, but zero exact duplicates exist anywhere. Any
near-repeat mechanism would have to be gated so prose stays free.

## B. The opening: the wire is dense, but the tape is not compressible

After a full-stack encode the wire's density is poor, and it is not a search
failure (`bench/x34/anat.ts`, `resid.ts`):

| lane | raw tokens | wire | tape chars | chars/token |
|---|---|---|---|---|
| openstack-loghub-26.log | 4028 | 945 | 1272 | 2.50 |
| git-numstat.txt | 4632 | 1992 | 3331 | 2.20 |

English prose runs at roughly **4.3** chars/token. The tape runs at 2.2–2.5.
Since the tape has zero residual repeat, that 2.2–2.5 **is the price of the
alphabet**, not of the search. No better search can touch it.

## D. The mechanism: alphabet arbitrage

o200k_base spends its long tokens on common English fragments and charges about
one token per character for anything else. Random hex *is* the anything else:

```
random hex, as-is                      1.740 chars/token
same information, re-spelled           2.201 chars/token   (random corpus)
same information, re-spelled           2.460 chars/token   (real corpus)
```

Nothing is lost and nothing is guessed — a fixed 16-character substitution is
information-preserving. The wire is shorter only because the vocabulary charges
less for letters it knows.

First sweep (`bench/x34/alpha.ts`, 78 hex runs, 2520 chars, baseline 1451 tok):

```
freqEN   'etaoinsrhldcumfp'   1050 tok   2.40 ch/tok   -27.6 %   <-- winner
vowelish 'aeioubcdfghjklmnp'  1111       2.27          -23.4 %
freqEN2  'etaoinshrdlcumwfg'  1145       2.20          -21.1 %
lowerMix 'thequickbrownfxjm'  1344       1.88           -7.4 %
digits   (identity)           1451       1.74            0.0 %
base64 of the same bytes      1059       1.78          -27.0 %  (but +33 % chars)
```

### Digit runs are explicitly NOT re-spelled (`bench/x34/dig.ts`)

The obvious generalisation — do this to digits too — **loses**, because bare
digits already tokenize at 2.16–2.80, at or above what any letter alphabet
achieves:

| lane | digit runs | base | mapped (best) | delta |
|---|---|---|---|---|
| find-listing.txt | 326 | 892 | 911 | **+19** |
| vix-daily-1990.csv | 630 | 1260 | 1412 | **+152** |
| openstack-loghub-26.log | 213 | 458 | 420 | −38 |
| dump.sql | 107 | 323 | 313 | −10 |
| ls-full-iso.txt | 91 | 210 | 197 | −13 |

Mixed results at best, catastrophic on the digit-heavy tables. Excluded.

## E. Choosing the alphabet: two searches that disagree

Hill-climbing over all 26-letter assignments, scored two ways:

| evaluation set | best alphabet | chars/token | saving |
|---|---|---|---|
| 900 deterministic random hex strings (`opt.ts`) | `etaoinsrkldcumyp` | 2.201 | −20.9 % |
| 663 real corpus hex runs, 9472 chars (`opt2.ts`) | `keaoinstrldcumzp` | 2.460 | −28.8 % |

They disagree. **End-to-end measurement settles it in favour of neither:**

| alphabet | dump.sql | openstack | total |
|---|---|---|---|
| `keaoinstrldcumzp` (better in isolation) | −52 | −14 | −66 |
| **`etaoinsrhldcumyp` (better end to end)** | **−54** | **−17** | **−71** |

Shipped: **`0123456789abcdef → etaoinsrhldcumyp`**, selected on the measured
full message, not on the isolated run score.

A second alphabet lesson, found earlier: position 7 (hex `7`) must be `h`, not
`k`. `etaoinsrhldcumfp` is −51 and `etaoinsrkldcumfp` is **+3** — one letter
flips the sign.

## F. Two soundness conditions, verified per run at encode time

**(a) The run must be self-delimiting.** A closing delimiter costs ~1 token per
run: 176 tokens against a 398-token saving at 88 runs, which eats the prize. So
the encoder instead *verifies* that every run it re-spells is followed by a
character outside the target alphabet (`bench/x34/bound.ts`):

```
openstack-loghub-26.log   88 runs   ' 'x62  '/'x15  ']'x7  ')'x2  CR x2
dump.sql                  26 runs   "'"x26
```

Every one is a non-letter, so "consume letters until a non-letter" is exactly
the true end of the run. If any document violates this, the run is skipped.

**(b) The marker must not occur in the source.** A free marker is chosen from
`['~','^','·','¦']`; if none is free, the transform is skipped.

## G. Why UNIFORM, not selective — the counterintuitive result

The obvious refinement is to re-spell only the runs that individually pay.
Measured, that refinement is **wrong**:

```
dump.sql   uniform remap (all runs >= 12)        -44 tokens
dump.sql   per-run remap (only runs that pay)    +37 tokens
```

Selective remapping leaves the document half in one alphabet and half in
another, destroying the regularity the grammar search depends on. A *uniformly*
re-spelled document is **more** regular than the original, so the search finds
better rules in it — the whole is worth more than the sum of its parts.

Consequently the per-run estimate is used only as a **weak gate** (skip the
second encode on documents with no hex at all), and the real decision is a
measured end-to-end comparison.

The gate was also too strong in its first form. Requiring
`estimated >= 2 x clause` **rejected a real −44 win** on dump.sql (estimated 29
against a threshold of 34): the isolated estimate is *pessimistic* there, not
optimistic, precisely because of the effect above.

**The isolated estimate is now not used to decide at all**, and that is measured
rather than assumed. It is the sharpest negative result in X34:

| alphabet | isolated estimate on dump.sql | actual delivered |
|---|---|---|
| first measured | 29 | −54 |
| shipped | **2** | **−54** |

The estimate moves by a factor of fourteen while the outcome does not move at
all. An estimate like that is not a signal, and gating on `estimated > 0` left a
real −54 one slightly-unlucky measurement away from being silently skipped. The
gate is therefore a character count and nothing else:
`hexChars >= 150`. The estimate is still computed and reported (`est=` in the
registry note) for diagnosis.

## I. External context (new this turn, not previously cited)

* **arXiv 2610.01127, "Counting and Min-Cost Encoding for Tokenization"
  (2026-10-01)** — the closest published statement of the mechanism. Given a
  **fixed** vocabulary, MCE selects a segmentation by *globally minimising an
  encoding cost*, and CNF-MCE beats BPE on token efficiency across six text
  categories. This is exactly the situation PYKNOSIS is in and is its
  justification: the decoder's vocabulary is **frozen** at o200k_base and
  cannot be retrained, so the only free variable is the character string handed
  to it — and choosing that string well is a real, measurable optimisation.
  They change the *vocabulary*; we hold the vocabulary fixed and change the
  *text*. Same objective, opposite side of the interface, and ours needs no
  cooperation from the model.
* **"The tokens-per-byte trap" (DEV, 2026-05-23)** — the failure mode this
  codec is one wrong design decision away from. It documents that deleting 25 %
  of characters makes prompts **23–66 % larger in tokens**, because corrupted
  prose no longer matches learned merges and falls through to byte-level
  fallbacks (up to 4 tokens per glyph). Its own prescription is the guard we
  apply: *"run your input through the actual tokenizer before AND after any
  compression scheme."* PYKNOSIS measures every candidate against the real
  o200k tokenizer and ships only strictly better — and it perturbs characters
  **into** the vocabulary's sweet spot (common letters), not out of it.
* **arXiv 2511.20849, "Length-MAX Tokenizer" (2025-11-25)** — 14–18 % fewer
  tokens than BPE by selecting longer tokens directly, attributing the gain to
  "longer tokens shorten effective dependency chains." Corroborates that token
  *length* is the lever; but it requires building a new tokenizer, which the
  one-chat constraint forbids. Reinforces X32's conclusion that with the
  decoder's tokenizer frozen there is no headroom in the merge rule itself —
  only in what string we feed it.

## J. Honest scope and limits

* **This is not a general-purpose compressor.** It pays on documents carrying
  hexadecimal payloads and is a no-op everywhere else, at the cost of one regex
  scan and a handful of token counts. Two lanes of 31 moved.
* **Cost on firing lanes:** the transform costs a second full encode
  (dump.sql 97 s → 189 s; openstack 102 s → 164 s). On no-op lanes the measured
  times are noisy in **both** directions, because the pipeline is **not
  deterministic** (`Date.now()` inside control flow in `polytropos.ts`,
  `akribeia.ts`, `aion.ts`, `abacus.ts`, `amphora.ts`; `OMEGA_DET=1` stubs only
  `clock.now()`). The gh-api +3 is the same effect.
* **Single measurements, not distributions.**
* **The alphabet was selected on two lanes' end-to-end results.** This is the
  weakest part of the work and it is stated as such: a third hex-heavy lane
  could plausibly prefer a different letter at some position, since the
  per-position effect was measured to be worth up to ~54 tokens.
* **Decodability.** The clause is 17 tokens and reads, appended to the TIMEMA
  tail: `Then ~: etaoinsrhldcumyp mean 0123456789abcdef. print only.` The
  re-spelling sits *under* the dictionary: the wire expands first and the
  alphabet is undone last, so the undo is a flat character operation over text
  in which every run still appears in its original surroundings.
* **Not done this turn:** the openai/math re-audit, the refreshed
  local-leader-by-category table, and confirmation of the 28-lane frontier.

### What changed relative to X33's snapshot

* **The catalog shrank.** 722 → 719 manuscripts inside 24 hours, on a sign
  error. X33 recorded "OpenAI withdrew three Hodge/Weil papers after a sign
  error"; the audit now pins the date (Oct 7) and the mechanism (one proof
  invalidated, two dependent constructions withdrawn with it).
* **The formalization share is now quantified and it is a minority.** ~42 % in
  Lean, so **just under 58 % of the release rests on natural-language proofs
  with no machine verification**. X33 had this only as the repository's own
  qualitative "unformalized results may have issues" warning.
* **The review status of the October formal proofs is "unchecked."** This is the
  sharpest new fact and the one most relevant to this project's own epistemic
  standards: the August files were labelled *agent-reviewed*, the October
  catalogue's formal proofs are labelled ***unchecked***. A Lean kernel check
  guarantees the proof object typechecks; it does **not** guarantee the formal
  *statement* says what the open problem asks.
* **Novelty and prior-art disputes widened** beyond the non-sofic-group result
  to **sphere packing and binary/spherical codes**.
* **Process transparency is contested**: only ~**1.4 %** (10 of 719) of
  manuscripts include chain-of-thought material, and an advisory group has
  requested machine-readable links between proofs and formal artifacts.

### Why this is recorded here

It is not evidence about compression. It is recorded because this repo's
standing contract is *honest receipts only* — every claim above is dated and
sourced, and the same standard is applied to the project's own numbers (see the
gh-api +3 and the package-lock OOM in §H, both reported rather than hidden).
The reusable lesson is the one Kyle Saunders draws and it transfers directly:
**"the gap between 'the proof goes through' and 'the statement is the
conjecture'"** is exactly the gap between *our wire round-trips* and *our wire
is optimal*. Lean's binary accept/reject is the analogue of our
`byteExact === true`: necessary, cheap, and nowhere near sufficient. The
"unchecked" label on a kernel-verified artifact is the strongest available
argument that a passing mechanical check is not a claim of correctness.
