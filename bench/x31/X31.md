# X31 — HEURESIS (εὕρεσις, "discovery")

**Codec shipped:** `src/lib/omega/heuresis.ts`, registered in
`src/lib/omega/registry.ts` as key `heuresis`, spec in
`docs/codec-abbreviations.md`.

**One-line result.** A search-budget codec: raise the glyph-script trial budget
from the hardcoded 3/2/3 to a floor of 4. **11 lanes measured, 3 improved, 0
regressed, all byte-exact, +3% encode time.**

---

## A. What the codec does

SYNTOMOS builds its glyph alphabet by merging character pairs into single-token
glyphs. A set of disjoint merge pairs can be realised by many different
pair → glyph **assignments**, and the assignment is not cosmetic: it decides
which substrings become glyph strings, hence the whole tape.

`renderBest` (`ariadne.ts`) cannot try all of them. It ranks candidate scripts
by merge-edge count and keeps the top `scriptTries`:

```
for (const cand of cands.slice(0, o.scriptTries ?? 2)) { ... }
```

`sibyl.ts` supplies that budget at three call sites, hardcoded **3 / 2 / 3**
(lines ~366, ~377, ~383 pre-patch). Nothing had ever varied it. HEURESIS raises
all three to a floor of 4 via a new `SibylOptions.minScriptTries` and the
`OMEGA_SIBYL_TRIES` env fallback.

**Why widening is safe by construction:** all three sites keep a *running best*
across the candidates they try, so a wider budget cannot lose a candidate
already found. It can only add.

## B. The one non-obvious result: higher is not better

At `tries=8`, ls-full-iso goes **373 → 374** — it gets *worse*. Extra renders
consume the lane's own search budget and starve the rule search downstream.
`tries=4` is the measured saturation point: a complete script search that has
not yet started to crowd out its neighbours.

**Widening a search blindly is not a win; widening it to saturation is.**

## D. Negative space — four levers measured and rejected

### D.1 Assignment memoization — DEAD (reverted)

`runCostPrepared` (`ariadne.ts`) is the hot function. Measured
(`bench/x31/rcp.ts`):

| lane | encode ms | calls | patterns scanned | rcp ms | share |
|---|---|---|---|---|---|
| kb-article | 16940 | 299 838 | 20 732 014 | 4518 | 27% |
| ls-full-iso | 82437 | 2 011 858 | 115 258 270 | 57 539 | 70% |
| email-thread | 43568 | 1 751 463 | 87 553 808 | 24 217 | 56% |

Built a whole-assignment memo keyed on the glyph of every rule present in
ascending rule-id order (collision-free: same key ⟺ same assignment),
`ASSIGN_MEMO_MAX = 4_000_000`.

**Measured hit rate (`MEMO_STATS`):**

| lane | hits / calls | rate |
|---|---|---|
| ls-full-iso | 11 460 / 1 985 176 | 0.6% |
| kb-article | 7 602 / 299 838 | 2.5% |
| email-thread | 14 763 / 1 751 463 | 0.8% |
| meeting-transcript | 5 588 / 432 442 | 1.3% |

Zero speedup (kb-article 16.9 → 17.4 s; ls-full-iso 82.4 → 84.3 s). Reverted
via `cp /tmp/ariadne.orig.ts src/lib/omega/ariadne.ts`.

**The cost is in the scan, not in repeat evaluation.** Do not retry.

**Faulty measurement to distrust:** an earlier `SIG`-based distinct-assignment
count reported an 83–94% hit rate. It built its key by iterating
`assign.values()` — Map *insertion* order, not rule order — which conflates
distinct assignments.

**Bug caught before shipping:** the memo was initially a module global, so two
different `PreparedRuns` with equal rule counts would collide and return each
other's costs. Scoped to the per-instance `p.memo`, guarded with `p.memo &&` so
a literal-built `PreparedRuns` takes the unmemoized path.

### D.2 Raising the time budget — DEAD

`budgetMs` 20 000 and 60 000 reproduce the default exactly on ls-full-iso
(373), prose-03 (843), prose-11 (804). The pipeline is not budget-starved at
the top level. Confirms X28.

### D.3 Widening the word/phrase rule grid — DEAD

`bench/x31/grid.ts`: `wordGrid [24,48,96]`, `[12,24,48,72]` and
`capGrid [16]` all reproduce the default byte-for-byte on prose-03 (843),
prose-11 (804), kb-article (628).

### D.4 Ungating the X30 bootstrap arm — DEAD

Run unconditionally (`OMEGA_X31_BOOTSTRAP=1`) it never wins outside its gate on
readme, prose-03, prose-11 or email-thread, and costs 20–50% extra runtime
(prose-11: 75 s → 96 s). The X30 gate
(`parent.rules === 0 || parent.parent === 'identity'`) is correctly tuned.

## G. Honest assessment

The shipped win is **small on tokens (−14 over 11 lanes) and concentrated on
ops lanes**, but it is free, general, regression-free, and costs the user 3%
more encode time on a search X30 already made 1.85× faster.

The more valuable output this turn is the **negative space**: five levers tried,
four killed with numbers, one shipped. D.1 in particular retires the single
most obvious remaining speed idea (memoize the 27–70% hot function) with a
measured hit rate rather than an argument.

**Not done this turn (carried forward):** the 28-lane sweep (4/28 across three
turns); new web searches on unreferenced sites; `openai/math` re-audit;
parallelizing the 8 sequential arms at `akribeia.ts:348`.
